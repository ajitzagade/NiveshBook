Never forced, never capped
Should Pay and Can Take are recommendations. Any actual amount is accepted — more, less, or exactly ₹0 — and the system reconciles the difference automatically (FR17, FR22).
Every suggestion stays editable
Next round's "Recommended Amount" carries forward prior pending/extra, but it's always a pre-filled, editable field — never an enforced number (FR19, FR24).
Percentages that always reconcile
Shares support 2 decimal places (e.g. 33.33%) with largest-remainder rounding, so a 3-way split of an odd amount still sums to exactly 100% — no leftover paise (FR13, AD-2).
One codebase, many clients
Branding, currency, locale, and which roles/modules are active are all environment configuration — verified by diffing two clients' deployed code and finding zero source differences (FR43).
Privacy enforced at the data layer
Every API route — including list, export, and report endpoints — re-checks the requester's live role and scope. A hidden nav item is also a blocked endpoint, not just a UI convention (AD-1, FR7-FR9).
Different projects, different partners
A partner's share is a record tied to one project, not a global relationship — so Project A and Project B can share some partners, none, or all, at different percentages each (architecture ERD; demonstrated live in the demo).
A money trail of any length
A withdrawal can split three ways, one of those legs can fund another project, that project can pay out again — and the whole chain stays navigable end to end, forward or backward, regardless of hop count (FR28, FR30).
Nothing is silently deleted
Every financial edit keeps its old value, who changed it, when, and why. A "delete" is always a cancellation plus a linked reversal record, never a hard remove (FR41, FR42, AD-5).
01 · Epic 1

Accounts, Roles & Access Control

Live now — in review

Every person gets a secure login, and the one server-side authorization gate everything else depends on is built and proven against a real action, not a stub.

  • Four roles, one gateFR6–FR8
    Every user is exactly one of: Owner/Admin, Partner, Sub-partner, or the optional Project Admin role (off by default, enabled per client). Every protected route calls the same authorize() check before touching data — there is no separate, weaker path for lists, exports, or reports.
    Scenario
    A direct API call that bypasses the UI entirely still receives a 403 with no data body — the check lives on the server, not in what buttons are shown.
  • Login, logout, and session controlFR1, FR5
    Standard credential login; logout invalidates the session server-side so a replayed token fails. Sessions expire after inactivity, and an Owner/Admin can revoke a session directly — the very next request on that token is rejected immediately.
  • Deactivate a user without losing their historyFR4
    An Owner/Admin can mark any user inactive. They can no longer log in, but every transaction they were ever party to remains intact and correctly attributed. Reactivating restores login immediately.
    Edge case
    A non-Owner/Admin attempting to deactivate any user — including themselves — is rejected with 403, proving the gate against a real destructive action.
  • Change your own passwordFR3
    A logged-in user updates their password with their current one as proof; a wrong current password makes no change.
  • Forgot / reset password
    Deferred by explicit client decision (23 Sep 2026) — not built for the current phase. When it ships: a time-limited, single-use reset link; identical response whether or not the email exists, so no one can probe which emails are registered.
  • Permissions area — who can approve whatFR45
    A dedicated screen shows which roles are enabled for this deployment (e.g. is Project Admin in use) and which specific users hold Owner/Admin-level approval authority — for example, who is allowed to authorize an Extra Withdrawal.
    Flexibility
    Revoking someone's approval authority here takes effect on their very next request — never a cached or stale permission carried over from an earlier login.
02 · Epic 2

Projects & Partner Shares

In development now

Create a project, assign validated ownership percentages to its partners, and let one level of sub-partnership split any partner's own share further.

  • Create a project with almost nothing requiredFR12
    A project needs only a name and a description to exist — no partners, no money, no share allocation required up front. Everything else attaches to it later.
  • Partner shares that must reconcile to exactly 100%FR13
    Adding or editing a partner's share shows a live running total. Under 100% shows how much remains; over 100% shows how much to reduce by. Percentages support 2 decimal places.
    Worked example
    Project A: Partner A 50%, Partner B 30%, Partner C 20% — the moment all three are entered, the screen shows Total Share: 100% ✓.
  • Sub-partners split their partner's share, not the projectFR14
    A sub-partner allocation is always a percentage of the full project — never "a percentage of my partner's percentage" — which keeps the math identical to the main partner table, one level down.
    Worked example
    Partner A's 50% splits into: Partner A's own 25%, Sub1 12.5%, Sub2 12.5% — each is a share of the whole project, not of Partner A's 50%.
  • Editing a share after transactions exist never rewrites history
    Changing a share percentage creates a new, dated version of that share. Every past transaction keeps the percentage that was actually in effect when it happened — no retroactive recalculation.
  • Different projects can have entirely different partners
    A share record is tied to one project, not shared globally across every project a person might be part of. So Project A and Project B are free to have the same partners, none of the same partners, or a mix — some carried over, some brand new — each at its own percentage.
    Shown live in the demo
    Project A's partners are Sandip Z, Yogesh Shilimkar, and ABC Group. Project B carries over Yogesh Shilimkar and ABC Group at different percentages, adds a brand-new partner (Kavita Joshi), and Sandip Z holds no share in it at all.
03 · Epic 2 (later stories)

Privacy & Visibility Between Partners

Specified — not yet built

Co-partners can never see each other's internal structure. Sub-partners see only their own slice, unless their own partner explicitly opts them into more.

  • Co-partner privacy boundaryFR9
    Partner B can never retrieve Partner A's sub-partner structure, private transactions, balance, or adjustments — not through the UI, and not by guessing a URL or ID directly. Owner/Admin is the one exempt role and sees everything.
  • A sub-partner sees only their own sliceFR10
    A sub-partner's dashboard, history, and reports are scoped to their own percentage only — never a sibling sub-partner's numbers, and never their parent partner's full internal split.
    Worked example (PRD's own journey)
    Sub1, one of Partner A's two sub-partners at 12.5% of the full project, opens their dashboard and sees only their own Should Pay / Paid Now / Pending figures. Editing the URL to try reaching Partner B's data returns "You don't have access to this" — no partial data, no error code, no hint of what would have been there.
  • A partner can optionally open up their own context to their sub-partnersFR11
    A Partner can grant their own Sub-partners visibility into partner-level context — this is opt-in, per partner, and only ever extends to that partner's own sub-partners, never to another partner's.
  • Per-partner visibility grants are themselves visible to Owner/AdminFR45
    The Permissions area (built in Epic 1) extends to show, per partner, whether they've turned that sub-partner visibility grant on or off.
04 · Epic 3

Add Money — Flexible Investment

Specified — not yet built

The system calculates what each partner should pay the moment a funding requirement is entered — and then accepts whatever they actually pay, tracking the difference automatically, forever.

  • Should Pay, calculated instantlyFR15, FR16
    An Owner/Admin enters one number — the amount a project needs — and Should Pay is computed for every partner from their Share %, then split again for any sub-partners, before anyone has paid a rupee.
    Worked example
    Project A needs ₹10,00,000. Should Pay: Partner A ₹5,00,000 (Partner A's own ₹2,50,000, Sub1 ₹1,25,000, Sub2 ₹1,25,000), Partner B ₹3,00,000, Partner C ₹2,00,000.
  • Paid Now can be anything — more, less, or nothingFR17
    Recorded across Cash, Cheque, NEFT, RTGS, IMPS, UPI, Bank Transfer, or Other. There is no minimum and no cap — Paid Now is never forced to match Should Pay.
  • Extra Paid and Pending, computed automaticallyFR18
    Pay more than Should Pay and the difference becomes Extra Paid. Pay less, and the shortfall becomes Pending. Pay exactly right, and no adjustment appears at all.
    Worked example
    Partner A pays ₹7,00,000 against a ₹5,00,000 Should Pay → Extra ₹2,00,000. Partner C pays ₹0 → Pending ₹2,00,000 — and the round proceeds for everyone else, unblocked.
  • Every adjustment carries forward, but stays editableFR19
    Next round's Recommended Amount is the new base share adjusted by whatever was Pending or Extra last time — shown side by side with the plain Normal Share, always pre-filled, never enforced.
    Worked example
    Partner A opens the next Add Money round and sees "Normal Share: ₹5,00,000" next to "After Previous Adjustment: ₹3,00,000" — free to pay either amount, or a different one entirely.
  • Sub-partner adjustments work identically, and stay privateFR20
    The same Should Pay → Paid Now → Adjustment → Carry Forward chain applies one level down for sub-partners, invisible to every other main partner.
  • Every entry is audited, editable, and reversible
    Correcting an amount preserves the old value, who changed it, when, and recomputes the adjustment. Cancelling never deletes — it marks the original cancelled and creates a linked reversal record.
05 · Epic 4

Withdraw Money & Cross-Project Movement

Specified — not yet built

The mirror image of Add Money for taking money out — plus the one capability that makes NiveshBook more than a ledger: a withdrawal can fund something else in the same action, and the link is never lost.

  • Can Take, calculated the same way as Should PayFR21
    Each partner's entitlement to withdraw is their Share % of whatever is available, computed with the same rounding rules that make the numbers always add up exactly.
  • Take Now can be ₹0 up to the full entitlementFR22, FR23
    Nothing forces a withdrawal. Whatever isn't taken becomes Keep for Later — tracked separately, not lost, not assumed to be reinvested.
  • Extra Withdrawal requires explicit Owner/Admin authorizationFR25
    Taking more than Can Take is not just "a bigger number" — it's rejected unless an Owner/Admin explicitly authorizes it as an Extra Withdrawal, which then reduces the partner's entitlement in future cycles.
  • One withdrawal, split across several destinations, in a single actionFR27
    A withdrawal can be allocated across another project, a person, and Available Balance all at once — save stays disabled until the split reconciles exactly to the withdrawn amount, and every leg commits or rolls back together.
    Worked example
    Partner A withdraws ₹2,50,000 and splits it: ₹1,50,000 → Project B, ₹50,000 → Person X, ₹50,000 → Available Balance. The screen won't save until it reads Distributed: ₹2,50,000 / ₹2,50,000 ✓.
  • Money sent to another project is auto-linked — never re-enteredFR28
    The ₹1,50,000 above doesn't just get subtracted from Project A — it appears in Project B automatically as a linked investment, in the same action, and the connection is navigable from either project.
    Also tracked, not lost
    Partners B and C, who withdrew nothing that round, still see their own untouched entitlement as Keep for Later ₹1,50,000 and ₹1,00,000 respectively on their dashboards.
  • Available Balance can never go negativeFR29
    The running wallet balance is protected by row-level locking, so two simultaneous spends can't both succeed and push it below zero.
  • The full money trail, any number of hops, both directionsFR30, FR32
    Original investment → withdrawal → three-way split → a later move out of Available Balance into a third project — the whole chain stays reconstructable and clickable from any single link in it, regardless of how many hops it took.
    Shown live in the demo
    The interactive demo traces one such chain 8 generations deep: a multi-partner + sub-partner funding round → withdrawal → 3-way split → one leg gets withdrawn and reinvested a third time, another leg funds a person who reinvests it fresh, and the last leg's Available Balance splits again into a later reinvestment and an Owner-approved Extra Withdrawal.
06 · Epic 5

Adjustments — Tracked Independently, Never Netted

Specified — not yet built

A person's investment ledger and their withdrawal ledger never touch each other automatically — because "you owe money on one side" and "you're owed money on the other" are different facts, not the same number.

  • Investment and Withdrawal adjustments, side by side, never mergedFR33, FR34
    The Adjust Next Time screen shows every person's pending/extra investment amount and their Keep for Later withdrawal amount as two separate sections — plain language, no formulas on screen.
  • Netting the two is a deliberate, audited action
    If an Owner/Admin does choose to offset one against the other, that's an explicit action in its own right — visible afterward in Money History as an "Adjustment" event, not something that happened silently in the background.
07 · Epic 5

Dashboards — One Screen, Three Shapes

Specified — not yet built

The same Home screen renders a different shape depending on who's looking — never a separate app, never a separate build.

  • Owner/Admin viewFR35
    Total project money, total added, total withdrawn, Available Balance, and a partner-wise overview — "a handful of cards, not a data dump."
  • Partner viewFR36
    My Projects, My Share %, Added, Withdrawn, Available Balance, Pending, Extra Paid, Keep for Later, and — if that partner has granted the visibility — their own sub-partners' summary.
  • Sub-partner viewFR37
    The identical categories as the Partner view, strictly scoped to that one sub-partner's own numbers.
08 · Epic 5

Reports — Ten Types, All Permission-Scoped

Specified — not yet built

Every report answers to the exact same access rules as every screen — a report is never a back door to data a role couldn't otherwise see.

  • Ten report typesFR38
    Project Money, Partner, Sub-partner, Money Added, Withdrawal, Available Balance, Money Movement, Payment Mode, Adjustment, and Money History reports.
  • Filter by date, project, or personFR39
    Every report can be narrowed the same three ways, consistently.
  • Export to Excel or PDFFR40
    What's exported matches what's on screen exactly — same scope, same filters, same numbers.
09 · Epics 3–5

Audit History & Trust

Specified — not yet built

Nothing about real money changes silently. Every edit leaves a record; nothing is ever hard-deleted.

  • Full before/after record on every editFR41
    Who changed it, when, the old value, the new value, and the reason if one was supplied — for any edited investment or withdrawal transaction.
  • Cancel and reverse, never hard deleteFR42
    A cancelled transaction stays visible, linked to its reversal record — both sides of the correction remain in the history, permanently.
  • A partner can see their own audit trail, not anyone else's
    Owner/Admin sees every audit record. A Partner or Sub-partner viewing their own transaction's history is permitted; requesting someone else's returns 403 — the same privacy rule applied one more place.
10 · Epic 1

Multi-Client Configurability

Live now — in review

NiveshBook was built from day one as a product to configure, not fork — a second client should never mean a second codebase.

  • Branding, currency, locale, and enabled roles — all configurationFR43
    A single client.config, resolved from environment variables at boot, controls how a deployment looks and which optional roles (like Project Admin) are switched on. No file anywhere in the application branches on which client it is.
    Verification, not a promise
    The team's own acceptance test for this: diff the deployed application code of two different clients and confirm the only differences are in configuration — never in source.
  • Sensible defaults, fully overridableFR44
    A new deployment defaults to INR with Indian digit grouping (₹10,00,000-style) unless a client's configuration says otherwise.

Not yet decided — flagged, not hidden

These are real open items from the product documents, not scenarios the app currently handles one way or another. Included here so this catalog doesn't imply more certainty than exists yet.

  • Whether Project Admin ships at all in this first phase, or waits — it's an optional role, deferrable per client.
  • The exact scope of what a partner can expose to their own sub-partners when they turn on the visibility grant (FR11) — needs one concrete worked example before it's built.
  • What the screen should say when two people edit the same record at the same time — the underlying data can't be corrupted (row-locking prevents that), but the on-screen message for "someone else just changed this" hasn't been designed yet.
  • The mobile experience below 860px width — the current mockup collapses the sidebar to a bare stack; the real build likely upgrades this to a proper slide-out panel, but that hasn't been confirmed.
  • Password-reset link expiry window — provisionally 30 minutes, unconfirmed, and the whole feature is deferred for now regardless.
  • Jurisdiction-specific real-estate-partnership compliance requirements — not yet addressed in the product requirements.
  • Performance and scale thresholds (dozens of projects, hundreds to low-thousands of transactions, dashboards under 2 seconds) are the working assumption pending confirmation at the architecture review stage.
