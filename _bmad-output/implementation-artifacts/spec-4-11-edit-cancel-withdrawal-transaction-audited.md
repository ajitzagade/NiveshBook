## Intent

**Problem:** `withdrawal_transactions` has no `status`/edit/cancel path at all — every Story 4.9/4.10 comment names this story as the one that closes it. Unlike the investment side (Story 3.7/3.8), a withdrawal can already be the root of a linked bundle (Story 4.8's auto-created destination `investment_transactions` + `money_movements`, Story 4.9's Available Balance credit) — cancelling it isn't a single-table operation, it's a cascade.

**Approach:** Mirrors Story 3.7 (edit) and Story 3.8 (cancel/reverse) on `investment_transactions` as closely as the domain allows — same mutable-fields-only edit shape, same never-hard-delete flip-status-plus-insert-reversal-row cancel shape, same `audit_log.idempotencyKey` reuse (Story 3.7's mechanism, not a new column), same two-layer not-cancelled guard, same 404/403 route ordering. `withdrawal_transactions` gains the identical `status`/`reversalOfTransactionId` columns Story 3.8 added to `investment_transactions`. Confirmed with the user 2026-09-25 on the two places this diverges from the investment-side precedent:

1. **Cancelling a withdrawal with a `"project"` leg** cascades by calling the *existing, unchanged* `InvestmentTransactionPort.cancelTransaction()` (Story 3.8) on the destination `investment_transactions` row (found via `money_movements`) — reused exactly as-is, no new cancel-shaped logic for that half. If that destination row has itself already been further withdrawn from (Story 4.9's `can-take` fix, which clamps to `"0"` rather than throwing), that's already handled — no new logic needed there either.
2. **Cancelling a withdrawal with an `"available_balance"` leg** attempts to reverse the credit by debiting the pool for the originally-credited amount, inside the same transaction. `available_balances` is the one table in this schema with a hard `CHECK (balance >= 0)` — if the pool's current balance is less than what this leg originally credited (because some or all of it was already spent onward, Story 4.9), `AvailableBalancePort.debitBalance()`'s existing `InsufficientAvailableBalanceError` propagates and the **entire cancellation rolls back** — nothing partially cancelled, the withdrawal stays active. No new "undo a spend" capability is built by this story; Owner/Admin must resolve the downstream spend first if this happens.
3. **`money_movements` rows are never touched by a cancel** — they stay exactly as-is, permanently (a historically-true "₹X moved from A to B on this date" fact; the cancellation signal lives entirely on the linked `investment_transactions.status`, mirroring how `money_movements` already has no `audit_log` row of its own per Story 4.8's Decisions).
4. **`withdrawal_destination_allocations` leg rows are never touched by a cancel either** — no new `status` column on that table. A pre-existing Story 4.7 schema comment speculatively suggested a hard-delete `ON DELETE CASCADE` unwind; that's superseded here by AD-5's never-hard-delete principle (already established one epic earlier by Story 3.8) — the parent `withdrawal_transactions.status` is the sole authoritative cancellation signal for the whole bundle.
5. **Editing `amount` is blocked once a destination allocation already exists** for this withdrawal (any legs recorded via Story 4.7) — a new precondition, since the allocation's legs must sum to the withdrawal's own `amount` (Story 4.7's `AllocationMismatchError`) and Story 4.10's reconciliation check would otherwise start flagging a real, permanent mismatch after a normal edit. Every other field (date/payment mode/reference number/notes) stays freely editable regardless of allocation status, mirroring Story 3.7 exactly.

## Boundaries & Constraints

**Always:** Cancelling a withdrawal's cascade (destination-investment-cancel for "project" legs, balance-debit for "available_balance" legs, the withdrawal's own status flip + reversal-row insert) is one DB transaction + one `audit_log` row (AD-5) — any cascade step's failure rolls back everything, no partial cancel. Both edit and cancel reuse `audit_log.idempotencyKey` (Story 3.7's mechanism, UNIQUE-when-present) for replay detection, never a new column. A two-layer not-cancelled guard: a fast pre-check in `packages/core`, an authoritative `SELECT ... FOR UPDATE`-scoped check in `packages/db` (mirrors Story 3.8's TOCTOU fix).

**Never:** No change to `moveWithdrawalToProject()`, `spendAvailableBalanceToProject()`, `assembleMoneyTrail()`, `reconcileMoneyTrail()`, or any existing investment-side edit/cancel function — every cascade step reuses `InvestmentTransactionPort.cancelTransaction()`/`AvailableBalancePort.debitBalance()` exactly as shipped. No new `status` column on `withdrawal_destination_allocations` or `money_movements` (this story's Decisions #3/#4). No editing of `sharePercentSnapshot`-equivalent fields, `partyType`/`shareId`/`projectId` identity, or the original `idempotencyKey` (mirrors Story 3.7). No self-access — Owner/Admin-only, matching every Epic 4 write action and this story's own AC ("Given a non-Owner/Admin user... 403").

## I/O & Edge-Case Matrix

| Scenario | Input / State | Expected Output / Behavior | Error Handling |
|----------|--------------|---------------------------|----------------|
| Edit, unallocated withdrawal (AC1) | Change amount/date/paymentMode/reference/notes, no legs yet | Saved in place, one `audit_log` "edit" row (old/new values, actor, when) | N/A |
| Edit amount, already-allocated withdrawal | Legs exist for this withdrawal | Rejected | `409 amount_locked_by_allocation` |
| Edit a non-amount field, already-allocated withdrawal | Legs exist, only date/paymentMode/reference/notes change | Saved normally — the allocation-lock only guards `amount` | N/A |
| Edit a cancelled withdrawal | `status: "cancelled"` | Rejected | `409 already_cancelled` |
| Idempotent replay of an edit | Same `idempotencyKey`, identical content | 200, `edited: false` | N/A |
| Cancel, "project" leg, destination not yet re-withdrawn (AC2) | Withdrawal has a Story 4.8 project leg | Original flips to `cancelled`, reversal row inserted, the destination `investment_transactions` row is also cancelled (its own reversal row too, via the unchanged Story 3.8 function) — atomically | N/A |
| Cancel, "project" leg, destination Project's pool already partly re-withdrawn | Can Take at the destination Project would go negative | Still succeeds — Can Take there clamps to `"0"` (Story 4.9's existing fix), no new guard needed | N/A |
| Cancel, "available_balance" leg, pool untouched since credit | Pool balance ≥ the amount this leg originally credited | Debited back to reflect the reversal, withdrawal cancelled | N/A |
| Cancel, "available_balance" leg, pool already partly/fully spent onward | Pool balance < the amount this leg originally credited | Entire cancellation rejected, nothing changes, withdrawal stays active | `409 insufficient_balance_to_reverse` |
| Cancel an already-cancelled withdrawal | `status: "cancelled"` | Rejected | `409 already_cancelled` |
| Idempotent replay of a cancel | Same `idempotencyKey`, identical content | 200, `cancelled: false` | N/A |
| Non-Owner/Admin caller, either action | Any other role | Rejected before any data read | `403 forbidden` |

## Implementation Notes

- **`sumActiveAmountByProjectId` on `WithdrawalTransactionPort` stays unmodified — deliberately.** Investigated first: this story adds `status` to `withdrawal_transactions`, which raises the question of whether "Taken" (Withdrawal Adjustment, Story 4.3) and Can Take's own downstream consumers should now exclude a cancelled withdrawal's amount, mirroring how Story 3.8 added `filterActiveTransactions` on the investment side. This story's own Code Map/Boundaries never name `withdrawal-adjustments/route.ts`, `my-withdrawal-status/route.ts`, or `WithdrawalTransactionPort.sumActiveAmountByProjectId` as files to touch — only the cascade to `InvestmentTransactionPort.cancelTransaction()`/`AvailableBalancePort.debitBalance()` is in scope. Left as an explicit, documented non-goal (a stale doc comment on that method was updated to say so) rather than silently extended — a real product question (should a cancelled withdrawal free up Can Take again?) that's out of this story's frozen scope to decide unilaterally.
- **The Edit dialog's "amount locked" precondition is a session-local signal, not a live read.** No `GET` endpoint exists to list a withdrawal's destination-allocation legs (the Code Map names only the two new PATCH/cancel routes), so `withdraw-money/page.tsx` tracks `allocatedWithdrawalIds` (a `Set<string>`, populated when `submitAllocation` succeeds in the current browser session) to decide whether to disable the Amount field and show the inline explanation pre-emptively. A withdrawal allocated in an earlier session (or by a concurrent user) still submits its amount edit normally from this page — the server's authoritative `409 amount_locked_by_allocation` guard (`packages/db`'s `editTransaction`, inside its own `FOR UPDATE` lock, using a fresh `listByWithdrawalTransactionId` read) is what actually enforces the rule either way, surfaced inline via the same `editFormError` mechanism every other edit-time error on this page already uses. This is a deliberate, scoped trade-off, not an oversight — building a new read endpoint/authorize action purely for this UI nicety was judged disproportionate to this story's own two-routes boundary.
- **The investment-side `AlreadyCancelledError` (propagated from `cancelWithdrawalBundle()`'s cascade, in the rare case a "project" leg's destination row was somehow already independently cancelled outside this withdrawal's own lifecycle) maps to the same 409 `already_cancelled` as `WithdrawalAlreadyCancelledError`** in `.../cancel/route.ts` — not a new response code. From the caller's perspective both mean "this couldn't be cancelled because part of the bundle already was"; inventing a second code for an edge case this rare (would require external state manipulation, since `cancelWithdrawalBundle` only reaches this path on a genuine, non-replay cancel attempt) was judged unnecessary API surface.
- **`cancelWithdrawalBundle()`'s reversal-row-linked leg lookup uses `MoneyMovementPort.findByWithdrawalDestinationAllocationId(leg.id)`** (keyed off the leg's own row id), mirroring `assembleMoneyTrail()`'s identical forward-walk precedent (Story 4.10) rather than inventing a new lookup shape.
- **Live-Postgres verification** (implementer, against a local Postgres via `docker`/`colima`, reachable throughout this session): a standalone script exercised, against the real DB layer (no HTTP layer, straight through `packages/db`'s ports): (1) editing a withdrawal's amount before any allocation exists (succeeds), allocating it, then attempting to edit its amount again (rejected with `WithdrawalAmountLockedByAllocationError`); (2) cancelling a withdrawal with a `"project"` leg — confirmed the destination `investment_transactions` row is also cancelled and the destination Project's live Can Take (via `sumActiveAmountByProjectId` + `computeCanTake`) drops back to reflect it; (3) cancelling a withdrawal with an `"available_balance"` leg whose pool was untouched — confirmed the pool reverses to exactly its pre-credit balance; (4) partly debiting that same pool directly (simulating Story 4.9's "already spent onward"), then attempting to cancel — confirmed `InsufficientAvailableBalanceError`, the pool left completely unchanged, and the withdrawal still `"active"`; (5) for every one of the above, reassembled the money trail from the withdrawal (`assembleMoneyTrail`) and confirmed `reconcileMoneyTrail` still reports `reconciled: true` with zero discrepancies. All scratch data (projects, users, requirements, shares, audit entries) was deleted afterward and the scratch verification script itself was removed (never committed).

## Review Triage Log

3-layer review (blind-hunter, edge-case-hunter, verification-gap) — no functional bugs found. All three reviews independently confirmed the cascade's transactional atomicity (an `InsufficientAvailableBalanceError` partway through a multi-leg cascade correctly rolls back everything already done in that call, including an earlier leg's investment-transaction cancel and the withdrawal's own would-be status flip), Open/Closed compliance (`moveWithdrawalToProject()`/`spendAvailableBalanceToProject()`/`assembleMoneyTrail()`/`reconcileMoneyTrail()`/the investment-side edit/cancel functions all genuinely untouched), and every architectural rule (AD-1/AD-5/AD-9, the two-layer not-cancelled guard, derived per-leg idempotency keys). Findings applied in one patch round (2026-09-25):

1. **[Low, documentation bug, found independently by two reviewers]** `WithdrawalTransaction.status`'s doc comment claimed a cancelled withdrawal "never counts toward Taken/Withdrawal Adjustment" — backwards from the actual (deliberately scoped-out) behavior, where `sumActiveAmountByProjectId` still sums every withdrawal row unconditionally. 2. **[Medium, verification gap]** `cancel-withdrawal-bundle.test.ts` never tested order-dependent error propagation across mixed legs (a successfully-processed leg followed by a failing one in the same call).
