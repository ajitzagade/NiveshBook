## Intent

**Problem:** Story 4.2 deliberately shipped with no cap against Can Take, explicitly deferring enforcement to this story. FR25 now requires that a withdrawal exceeding Can Take be rejected unless an Owner/Admin (holding the existing, currently-unconsumed `users.canApproveExtraWithdrawal` capability from Story 1.7) takes a distinct authorization action — not just a bigger number.

**Approach:** No UX spec exists for the authorization step's mechanics (confirmed absent from DESIGN.md/EXPERIENCE.md/epics.md). Resolved by extending this codebase's own established pattern for "a distinct authorization action" — Story 3.8's Cancel Payment confirmation dialog (separate modal, no editable fields) — rather than a checkbox on the same form (confirmed with the user 2026-09-24). When Take Now exceeds the target's live Can Take, the Record Withdrawal dialog's normal submit is intercepted and an "Authorize Extra Withdrawal?" confirmation dialog opens instead; confirming resubmits with `extraWithdrawalAuthorized: true`. A new `packages/core/src/extra-withdrawal.ts` function gates this server-side (defense in depth, not UI-trust) — a new, additive check, not a rewrite of Story 4.2's already-shipped `recordWithdrawalTransaction` (Open/Closed): the route independently recomputes the target's live Can Take via the existing `computeCanTake` (cheap, pure, no I/O) and calls the new gate before `recordWithdrawalTransaction` runs. No new `withdrawal_transactions` column (confirmed with the user 2026-09-24) — a row's mere existence with `amount > canTakeSnapshot` already proves it passed the gate, since an unauthorized excess is rejected before any write; Story 4.3's Withdrawal Adjustment already derives `extra_taken` from that comparison with no new column, satisfying AC3 with zero additional work (confirmed algebraically in Story 4.4).

**Decisions (resolved 2026-09-24):**
- **Self-access never covers an amount exceeding Can Take**, regardless of who normally has self-access to that share. AC4's framing ("non-Owner/Admin attempts to authorize their own Extra Withdrawal → 403") means the existing `withdrawal_transactions:create` self-access authorize() call runs unchanged first (as today); the new gate runs immediately after and independently re-confirms `actor.role === "owner_admin"`, rejecting any non-Owner/Admin regardless of the self-access outcome.
- **Two failure modes, two status codes.** Not Owner/Admin, or Owner/Admin with `canApproveExtraWithdrawal: false` (a revoked grant) → `403 forbidden` (uninformative, matching FR8 — no hint about *why*, consistent with every other role-based 403 in this codebase). Owner/Admin with the capability, but `extraWithdrawalAuthorized` missing/false on the request → `400 extra_withdrawal_authorization_required` with a specific, actionable message (distinct from a generic 403 — the actor *can* do this, they just haven't taken the distinct action yet).
- **`compareMoney`, never raw comparison**, to decide "exceeds Can Take" (AD-2).
- **Story 4.2's user-facing dialog copy and JSDoc claiming "no cap is enforced" are now false and must be corrected** as part of this story, not left stale.
- **Story 1.7's two deferred risks become live the moment this ships** (`deferred-work.md`: no guard against revoking the last remaining approver or self-revoking one's own grant; no audit trail on `PATCH /api/permissions/[userId]` grant/revoke) — out of scope for this story's Code Map (they're Story 1.7's own surface, not Story 4.5's), but flagged here so review doesn't treat them as newly-introduced.

## Boundaries & Constraints

**Always:** The extra-withdrawal gate runs after the existing self-access `authorize()` call, before `recordWithdrawalTransaction`. Every rejection path is checked server-side regardless of what the UI sends or hides. `extraWithdrawalAuthorized` is only ever consulted when `amount > canTake`; a normal (within-entitlement) withdrawal is entirely unaffected by this story — no behavior change for the common case.

**Never:** No new `withdrawal_transactions` column. No change to `recordWithdrawalTransaction`'s existing signature/contract. No reason/comment field collected for the authorization (matches Cancel Payment's precedent — `reason: null`). No change to Story 4.3/4.4's Extra Taken/carry-forward computation (already correct, algebraically, per Story 4.4).

## Code Map

- `packages/core/src/extra-withdrawal.ts` (new) — `OwnerAdminRequiredForExtraWithdrawalError`, `ExtraWithdrawalAuthorizationRequiredError` (local error classes, mirroring `withdrawal-transaction.ts`'s Open/Closed precedent); `assertExtraWithdrawalAuthorized(input: { requestedAmount: Money; canTake: Money; actorRole: UserRole; actorCanApproveExtraWithdrawal: boolean; extraWithdrawalAuthorized: boolean }): void` — no-op if `compareMoney(requestedAmount, canTake) <= 0`; otherwise throws `OwnerAdminRequiredForExtraWithdrawalError` if `actorRole !== "owner_admin"` or `!actorCanApproveExtraWithdrawal`, else `ExtraWithdrawalAuthorizationRequiredError` if `!extraWithdrawalAuthorized`.
- `packages/core/src/index.ts` — barrel-export the new module.
- `apps/web/app/api/projects/[id]/withdrawal-transactions/route.ts` — after the existing `authorize()` self-access call and before `recordWithdrawalTransaction`: call `computeCanTake(availableToWithdraw, partnerShares, groupByPartnerId(subPartnerShares))` (already-imported pure function, cheap to recompute — mirrors this route's own existing "call pure functions freely" pattern rather than threading a value through `recordWithdrawalTransaction`'s stable signature), extract the target's `canTake` from the result tree, fetch `session.userId`'s full `User` row via `userPort.findUserById` for `role`/`canApproveExtraWithdrawal`, call `assertExtraWithdrawalAuthorized`, map its two errors to `403 forbidden` / `400 extra_withdrawal_authorization_required`. Update the route's own JSDoc (currently states "no cap... is enforced here") to reflect the new gate.
- `apps/web/app/api/projects/[id]/withdrawal-transactions/shared.ts` — add `extraWithdrawalAuthorized?: boolean` to `ValidWithdrawalTransactionBody`'s type guard (optional, defaults `false`/absent).
- `apps/web/lib/withdrawal-transactions.ts` — add `extraWithdrawalAuthorized?: boolean` to the client `RecordWithdrawalTransactionInput`, passed through unchanged to the `POST` body.
- `apps/web/app/(dashboard)/projects/[id]/withdraw-money/page.tsx` — `handleRecordWithdrawalSubmit`: before calling `recordWithdrawalTransaction`, compare `recordAmount` against the target's current `canTake` (already available from `state.partners`/`findPartnerAdjustment`-style lookup used elsewhere on this page) via `compareMoney`; if it exceeds, open a new "Authorize Extra Withdrawal?" confirmation dialog (mirrors Add Money's Cancel Payment dialog shape: `DialogTitle`/`DialogDescription` stating the excess amount, Confirm/Cancel buttons with icons per DESIGN.md's convention, no editable fields) instead of submitting directly; confirming calls the same submit path with `extraWithdrawalAuthorized: true`. Correct the existing dialog copy that currently states no cap is enforced.

- Given Partner A's Can Take is ₹2,50,000, when Owner/Admin explicitly authorizes an Extra Withdrawal, then Partner A can withdraw ₹3,00,000, and the excess ₹50,000 is recorded as Extra Taken.
- Given the same scenario, when the withdrawal is attempted without the explicit authorization step, then it's rejected — Extra Withdrawal requires a distinct authorization action, not just a bigger number (FR25).
