## Intent

**Problem:** FR29's Available Balance ledger doesn't exist. Story 4.7's `"available_balance"` destination leg currently only writes a `withdrawal_destination_allocations` row (amount + notes) with zero ledger effect — confirmed by `packages/types/src/index.ts:433-436`'s own doc comment naming this story as the one that adds the credit. There's also no way to *spend* a balance once held, and no page to see it. Separately, investigation surfaced a real, pre-existing bug: `GET /api/projects/[id]/can-take`'s `availableToWithdraw` has never been reduced for money already withdrawn (its own code comment names Stories 4.2/4.9 as the fix, but Story 4.2 didn't touch it) — Can Take doesn't shrink after a withdrawal today.

**Approach:** Confirmed with the user 2026-09-25:
1. **Scoping:** `available_balances` is keyed by `(partyType, shareId, projectId)` — the *source* Project the withdrawal came from — mirroring `withdrawal_adjustments`' exact precedent, not a cross-Project per-person balance (which would need `users.id`-based scoping, violating AD-4, and has no resolution for a Partner with no linked login). The *spend destination* is unconstrained to that source Project.
2. **Can Take fix is in scope**: `availableToWithdraw` becomes `subtractMoney(totalActiveInvested, totalActiveWithdrawn)` for the Project (AD-2). `computeCanTake`'s pure signature is untouched — only the route's resolution step changes, per its own doc comment's promise.
3. **UI is Project-scoped** (`/projects/[id]/available-balance`), not a cross-Project aggregate — confirmed by the sidebar's own pre-existing inert nav item (`layout.tsx:51`, comment: "Available Balance... still backlog", awaiting an `href: "/projects"` flip exactly like Withdraw Money's own activation) and by this app's universal precedent (every Partner/Sub-partner list is Project-scoped; `partnerId` itself is minted fresh per Project, so no cross-Project person-identity mechanism exists to aggregate against).
4. **Credit** happens inside the *existing* `recordAllocation` transaction (Story 4.7/4.8), extending its per-leg loop: an `"available_balance"` leg now also credits `(withdrawalRow.partyType, withdrawalRow.shareId, sourceProjectId)` — same replay-safety as the existing `"project"`-leg branch (only reached on a genuine first write, never on replay).
5. **Spend** is a new action + page: `POST .../available-balance/spend`. "Invest in a Project" reuses `buildTransactionSnapshot`/`recordTransaction` via a new sibling orchestration function `spendAvailableBalanceToProject()` (Open/Closed — `moveWithdrawalToProject()` stays untouched, a new additive function mirrors its shape for this call site). "Give to a Person" just debits the balance and records a spend row, no linked `investment_transactions` (mirrors Story 4.7's `"person"` leg — no Person entity exists).
6. **`money_movements` (Story 4.8, done) gains one new optional linking column** — non-breaking, mirrors 4.8's own precedent of adding nullable columns to a previous story's shipped table: `withdrawalDestinationAllocationId` becomes nullable, new nullable `availableBalanceSpendId` added. Exactly one of the two is set per row (an allocation-sourced movement, or a spend-sourced movement) — existing `moveWithdrawalToProject()` callers are unaffected (they keep passing `withdrawalDestinationAllocationId`, never touch the new field).
7. **Row-lock discipline (AD-10)**: credit uses an atomic upsert (`balance = balance + amount`, no lost-update risk without an explicit lock). Debit uses `SELECT ... FOR UPDATE` on the balance row, then `assertSufficientBalance` (pure, `compareMoney`-based, AD-2), then `UPDATE`, inside one transaction — plus a Postgres `CHECK (balance >= 0)` backstop (first such constraint in this schema).

## Boundaries & Constraints

**Always:** Every balance-decrementing mutation takes a row lock before checking sufficiency and writing (AD-10, no exceptions). Credit only ever fires on `recordAllocation`'s first-write branch, never on replay. The destination requirement/share for an "Invest in a Project" spend is re-resolved server-side against *current* data at save time, never client-trusted (mirrors Story 4.8's identical rule). Spend is one DB transaction + one `audit_log` row + a client idempotency key (AD-5). `assertSufficientBalance`/the debit path is the only place balance sufficiency is decided — never inferred from a client-supplied "current balance" figure.

**Never:** No cross-Project balance aggregation or a `users.id`-keyed balance (this story's Decisions #1). No change to `moveWithdrawalToProject()`'s or `buildTransactionSnapshot`'s/`recordInvestmentTransaction`'s existing signatures. No change to Story 4.7/4.8's `"project"`/`"person"`/`"other"` leg handling — only the `"available_balance"` leg gains new behavior. No synthetic Person entity for "Give to a Person" (mirrors 4.7's `"person"` leg exactly — free-text name only).

## I/O & Edge-Case Matrix

| Scenario | Input / State | Expected Output / Behavior | Error Handling |
|----------|--------------|---------------------------|----------------|
| Credit (AC1) | ₹50,000 `"available_balance"` leg saved via Story 4.7/4.8's allocation flow | `available_balances` row for that (partyType, shareId, sourceProjectId) created/incremented to ₹50,000; visible on the Project's Available Balance page | N/A |
| Debit into a Project (AC2) | ₹30,000 spent from a ₹50,000 balance, destination Project C, existing requirement + share | Balance → ₹20,000; a real `investment_transactions` row exists at Project C with the correct snapshot; linked via `money_movements` | N/A |
| Debit to a Person | ₹X spent, destination "Give to a Person", free-text name | Balance decreases by ₹X; an `available_balance_spends` row records it; no `investment_transactions`/`money_movements` row (mirrors 4.7's `"person"` leg) | N/A |
| Overdraft attempt (AC3) | Spend amount > current balance | Rejected, balance unchanged | `409 insufficient_balance` |
| Concurrent double-spend race (AC4) | Two concurrent spend requests against the same balance, combined amount exceeds it | Exactly one succeeds; the other sees the post-first-spend balance and is correctly rejected (or both succeed if the balance covers both) — never a lost update, never negative | `409 insufficient_balance` for whichever loses the race |
| Idempotent replay of a spend | Same spend `idempotencyKey`, identical content | 200 replay — no duplicate debit, no duplicate `investment_transactions`/`money_movements`/spend row | N/A |
| Zero/negative spend amount | `amount` ≤ 0 | Rejected — mirrors Story 4.8's `ZeroAmountProjectLegError` precedent for the identical class of bug | `400 validation_error` |
| Can Take after a withdrawal (fix) | Project has ₹10,00,000 invested, ₹2,00,000 already withdrawn (active) | `availableToWithdraw` = ₹8,00,000, not ₹10,00,000 | N/A |
| Chosen destination requirement/share stale at spend time | Deleted/changed between fetch and submit | Rejected | `404 not_found` (mirrors Story 4.8) |

## Implementation Notes

- **`spendAvailableBalanceToProject()` vs `moveWithdrawalToProject()`: no shared private helper.** The spec left this to the implementer. Chose NOT to extract one — the two functions are near-identical but small (~35 lines), and keeping them fully independent guarantees `moveWithdrawalToProject()` stays byte-for-byte untouched (Open/Closed), which felt like a stronger guarantee than saving ~20 duplicated lines behind a helper. `spendAvailableBalanceToProject()` mirrors it verbatim except: `moneyMovements.record()` passes `availableBalanceSpendId: spendId, withdrawalDestinationAllocationId: null` instead of the reverse.
- **`GET .../available-balance` response shape**: `{ partners: [{ partnerId, name, sharePercent, balance, subPartners: [{ subPartnerId, name, sharePercent, balance }] }] }` — mirrors Can Take's/Withdrawal Adjustment's nested-Partner-with-subPartners shape (not a flat list) so the client can reuse the same "Partner row, indented Sub-partner rows" `Table`/`TableRow subRow` rendering convention as every other list page. A share with no `available_balances` row yet resolves to `balance: "0"` (plain, unformatted — matches `toMoney`'s own un-padded-zero convention), never omitted from the response.
- **`POST .../available-balance/spend` response shape**: `{ spend: AvailableBalanceSpend, investmentTransaction: InvestmentTransaction | null, moneyMovement: MoneyMovement | null }` — the latter two are `null` for a `"person"` spend, populated for a `"project"` spend. Status is `201` on a genuine create, `200` on an idempotent replay (mirrors every other write route in this codebase).
- **Spend amount validation lives in the route, not a new `packages/core` module.** The Code Map's `packages/core` file checklist doesn't list a `record-available-balance-spend.ts`-style domain module (unlike `withdrawal-destination-allocation.ts`'s `recordDestinationAllocation`, which exists because it has a real cross-leg sum invariant to check). A single spend has no such invariant, so `toMoney`/`isZeroMoney` (both already exported by `@niveshbook/core`) are called directly in `spend/route.ts` — `toMoney` rejects a malformed/negative amount (`InvalidMoneyError` → 400), `isZeroMoney` rejects exactly `"0"` (this story's I/O matrix: unlike an allocation leg, a spend is never a legitimate no-op).
- **No "is this a current share" check on the spend's source `(partyType, shareId)`.** The Code Map's route description doesn't call for one, and `available_balances` is scoped by `(partyType, shareId, projectId)` independent of whether that person is still a *current* Partner/Sub-partner Share today — a person who left after being credited should still be able to have their leftover balance spent by an Owner/Admin. `debitBalance` naturally handles a nonexistent/never-credited key as a `"0"` balance (→ `InsufficientAvailableBalanceError` for any positive amount), so this needs no separate existence check.
- **A `"project"` spend's destination is NOT required to differ from the source Project** — deliberately unlike Story 4.7/4.8's withdrawal-allocation `"project"` leg (`InvalidDestinationProjectError`). This is spec-4-9's Decisions #1 verbatim ("the spend destination is unconstrained to that source Project") — reinvesting a balance back into the Project it came from is a legitimate spend. Verified live (see below).
- **`DestinationRequirementAndSharePickers` extraction**: moved to `apps/web/app/(dashboard)/projects/[id]/destination-picker.tsx` (a non-route file colocated one level above both `withdraw-money/` and `available-balance/`, so both import it via `../destination-picker`). Took the lazy-fetch-per-destination-Project state/caching with it as a new `useDestinationProjectData()` hook (previously inline `useState`/`useRef`/`loadDestinationProjectData`/`ensureDestinationProjectData` in `withdraw-money/page.tsx`) — `withdraw-money/page.tsx`'s own 61 pre-existing tests passed unmodified after the extraction, confirming it's behavior-preserving. The picker's `leg`/`onChange` props were narrowed to a new `DestinationSharePickerFields` interface (just `destinationRequirementId`/`destinationShareId`/`destinationPartyType`) rather than the withdraw-money page's full `AllocationLegForm`, so the Available Balance page's own (differently-shaped) spend-form state satisfies it structurally with no adapter needed.
- **Real bug found and fixed in `packages/db/src/ports.ts`'s `isUniqueViolation`** (pre-existing, not introduced by this story): this drizzle-orm version (`0.45.3`) wraps a query error thrown inside `database.transaction(async (tx) => {...})` in a `DrizzleQueryError`, whose own `.code` is `undefined` — the raw `PostgresError.code` lives one level down at `.cause.code`. The old check (`"code" in error`) never actually matched this wrapped shape, so *every* existing concurrent-double-submit-recovery path in this file (`createWithdrawalTransactionPort.recordTransaction`, `createInvestmentTransactionPort.recordTransaction`, `createWithdrawalDestinationAllocationPort.recordAllocation`) was silently flaky under a real race — confirmed by running their own existing concurrent-race tests 5x in a row pre-fix (intermittent failures) and 5x post-fix (all green). Fixed `isUniqueViolation` to check both `error.code` and `error.cause?.code`; added direct unit-test coverage for the wrapped shape in `ports.test.ts`. This was caught by this story's own new `available-balance-spend-port.test.ts` concurrent-race test failing intermittently during development.
- **Live verification (2026-09-25, against local Docker Postgres + `next dev`, via seeded user + `curl`)**: all steps in the spec's Verification section below were exercised end-to-end and passed — Can Take shrank ₹10,00,000 → ₹8,00,000 after a ₹2,00,000 withdrawal; that withdrawal's `available_balance` leg credited the ledger to exactly ₹2,00,000; a ₹1,20,000 "Invest in a Project" spend (destination = a *different* Project) correctly debited the balance to ₹80,000 and created a real `investment_transactions` row at the destination (confirmed via that Project's own `transactions`/`should-pay`/`adjustments` endpoints — `actualPaid: "120000.00"`); an overdraft attempt (₹9,99,999 against an ₹80,000 balance) was rejected `409 insufficient_balance` with the balance left unchanged. Test data cleaned up afterward (no leftover rows).
