## Intent

**Problem:** FR-40 asks for reports to be exportable "to Excel and to PDF/print" — the AC's second clause ("the exported data matches exactly what was shown on screen — no additional or missing rows") is the real acceptance bar. No export/file-generation library of any kind exists in this codebase yet (confirmed by exhaustive grep of `apps/web`/`packages` and both `package.json` files) — this story is the first to need one. Story 5.7 explicitly scoped this out ("Report Export ... Story 5.8's job entirely").

**Approach:** Confirmed with the user 2026-09-25:
1. **Export is entirely client-side, reusing the report viewer's already-fetched, already-filtered rows** — `apps/web/app/(dashboard)/reports/[type]/page.tsx`'s existing `state.rows` (populated by `getReport()`, Story 5.7) is serialized directly into the exported file. No new API route, no second server-side fetch. This guarantees the AC's "matches exactly what was shown on screen" property BY CONSTRUCTION (the exported rows are literally the same in-memory array the visible table renders from, not a fresh re-fetch that could diverge if data changed between page load and export click) — a structural guarantee, not something that needs separate verification after the fact.
2. **No new `authorize.ts` action, no new AD-1 authorization call.** AD-1 binds `app/api/**/route.ts` Route Handlers; this story adds none. The rows being exported already passed through `GET /api/reports/[type]`'s existing `authorizeScope()` check (Story 5.7) before ever reaching the browser — export only ever serializes data the actor was already authorized to see and is already looking at on screen.
3. **Excel via `exceljs`** (new dependency) — actively maintained on npm, no known audit red flags. **PDF via `jspdf` + `jspdf-autotable`** (new dependencies) — the standard client-side pairing for generating a real, downloadable PDF file from tabular data (not a browser print dialog). All three are added to `apps/web/package.json`; `pnpm audit` must show zero vulnerabilities before this story merges (AGENTS.md's existing, unconditional gate — same one the Next.js 16.2.10→16.3.6 pin and the `esbuild` override already had to clear).
4. **Both generation libraries are dynamically imported** (`await import(...)`) inside the export functions, never imported at module top level — code-split so their JS weight only loads into the browser the moment a user actually clicks Export, not on every visit to a report page.
5. **A new `apps/web/lib/report-export.ts`** (pure client-side module — `Blob`/`URL.createObjectURL`/`document.createElement("a")` browser APIs) exports `exportReportToExcel(slug, rows)` and `exportReportToPdf(slug, rows)`. Each resolves the row family from `slug` (mirrors `ReportTable`'s own existing slug-to-family dispatch, Story 5.7) and builds the file using the EXACT SAME 6 column layouts as the 6 existing on-screen table components (`EntryRowsTable`/`PaymentModeTable`/`ProjectMoneyTable`/`PartnerTable`/`SubPartnerTable`/`AvailableBalanceTable`, `reports/[type]/page.tsx`) — see Decision #6 for the frozen column list per family. This file is new, separate from `apps/web/lib/reports.ts` (data-fetching) — Interface Segregation, a different concern.
6. **Frozen column-to-cell mapping, one row shape per family** (must match `reports/[type]/page.tsx`'s current rendering exactly, cited by line):
   - **Entry-based** (`money-history`/`money-added`/`withdrawal`/`money-movement`/`adjustment`, `page.tsx:75-121`): `Date | What Happened | Project | Person | Amount | Payment Mode | From | To | Notes` — 9 columns. "What Happened" = `ENTRY_TYPE_LABELS[entry.type]` (already exported from `@/lib/money-trail-view`, reused not duplicated) plus `" — Cancelled (reversal)"`/`" — Cancelled"` suffix text when `entry.status === "cancelled"` (the on-screen `StatusChip` badge has no export equivalent, so its text content is appended inline instead). `Amount` formatted via `formatAmount` (`@niveshbook/ui`, reused not duplicated — the same function `<Amount>` itself calls). `Payment Mode`/`Person`/`From`/`To`/`Notes` use the same `?? "—"` fallback and the same `PAYMENT_MODE_LABELS` map as the page (duplicated locally in `report-export.ts`, mirroring this codebase's own established per-module local-helper convention for exactly this kind of small lookup map — same convention `formatSharePercent` already follows across `home/page.tsx`/`reports/[type]/page.tsx`).
   - **`payment-mode`** (`page.tsx:123-146`): `Payment Mode | Total Amount | Entries` — 3 columns.
   - **`project-money`** (`page.tsx:148-177`): `Project | Money Added | Money Withdrawn | Available Balance` — 4 columns.
   - **`partner`** (`page.tsx:179-212`): `Partner | Project | Share % | Money Added | Money Withdrawn | Available Balance` — 6 columns. Share % via a locally-duplicated `formatSharePercent` trim (same convention as above).
   - **`sub-partner`** (`page.tsx:214-247`): `Sub-partner | Project | Share % | Money Added | Money Withdrawn | Available Balance` — 6 columns, identical shape to `partner` with a relabeled first column.
   - **`available-balance`** (`page.tsx:249-272`): `Name | Project | Balance` — 3 columns.
7. **The Export control is a `DropdownMenu`** (`packages/ui`, already installed/exported, unused elsewhere until now) labeled "Export ⌄" with two items, "Export as Excel" and "Export as PDF" — placed on `reports/[type]/page.tsx` near the existing filter controls. Disabled (or hidden) whenever `state.status !== "loaded"` or `state.rows.length === 0` — exporting nothing is not a valid action. Filename convention: `{report name}-{YYYY-MM-DD}.xlsx`/`.pdf`, using `getReportDefinition(slug).name` (Story 5.7) for the human-readable report name.
8. **The exported file always reflects whatever filters are currently applied on screen** — since export serializes `state.rows` directly (Decision #1), a filtered view exports only the filtered rows, matching the AC's "matches exactly what was shown on screen" wording literally (not a separate "export everything" path).
9. **`reports/[type]/page.tsx`'s 6 existing table components are NOT refactored or touched** — this story adds export as an independent, new capability reading the same `state.rows`, rather than editing Story 5.7's just-shipped, just-reviewed rendering code (Open/Closed). The frozen column list in Decision #6 is a documented, spec-verified mirror of those components' current columns, the same "hand-maintained mirror of another module's source of truth" pattern `report-catalog.tsx`'s own `roles` field already uses relative to `authorize.ts` (Story 5.7's own disclosed, accepted pattern) — reviewers can directly diff the export's column list against the live page's rendered columns.

## Boundaries & Constraints

**Always:** Every exported money value goes through `formatAmount()` (`@niveshbook/ui`), never a raw string interpolation of a `Money` value — this is the codebase's one shared money formatter and must stay the only one (mirrors AD-2's spirit at the display layer). `pnpm audit` must show zero vulnerabilities for the 3 new dependencies before this story is considered done (AGENTS.md's existing, unconditional gate). Export always operates on the CURRENTLY LOADED, CURRENTLY FILTERED `state.rows` — never a fresh fetch, never an unfiltered fetch (Decisions #1/#8).

**Never:** No new `authorize.ts` action, no new `app/api/**` route (Decision #2). No editing of `reports/[type]/page.tsx`'s 6 existing table components (Decision #9). No top-level (non-dynamic) import of `exceljs`/`jspdf`/`jspdf-autotable` anywhere in the client bundle (Decision #4). No change to `apps/web/lib/reports.ts`'s existing `getReport()`/`ReportFiltersInput`/`ReportRow` shapes.

## Implementation Notes

**Followed the Code Map's overall shape (`apps/web/lib/report-export.ts` exporting `exportReportToExcel`/`exportReportToPdf`, a `DropdownMenu` added to `reports/[type]/page.tsx`, both generation libraries dynamically imported) with two deliberate deviations and one unanticipated addition, all documented below.**

**Deviation #1 -- the 6 column-layout builds live in one shared internal helper, `buildExportTable(slug, rows) -> { headers, body }`, not duplicated logic inside each of the two exported functions.** The Code Map describes the column mapping per family but doesn't mandate an internal shape. Centralizing it means `exportReportToExcel` and `exportReportToPdf` are BOTH built from the exact same header/body arrays -- the two formats structurally cannot drift onto different content for the same `rows`, which is stronger than "both were implemented to match the same spec" (two hand-written copies that happen to agree today). Mirrors `ReportTable`'s own slug-dispatch shape in `reports/[type]/page.tsx:275-290` (same switch, same default-branch-covers-5-entry-types structure), so a reviewer can diff the two switches directly.

**Deviation #2 -- the Export dropdown's trigger is a raw `<button>` reusing the `nb-btn nb-btn-ghost` CSS classes, not the shared `Button` component.** `Button` (`packages/ui/src/components/button.tsx`) is a plain function component with no `forwardRef`; Radix's `DropdownMenuTrigger asChild` clones its child via `Slot`, which needs a ref-forwarding host to position the popover correctly. `ProjectSwitcher.tsx` -- this codebase's only other `DropdownMenuTrigger asChild` usage -- already established a raw `<button>` as the correct pattern for exactly this composition; this story follows that same precedent rather than risk a broken/mispositioned menu. To stay pixel-consistent with `Button`'s own ghost variant despite not using the component, the trigger reuses the literal `nb-btn`/`nb-btn-ghost` CSS classes `Button` itself emits (`packages/ui/src/styles/tokens.css`) -- no new visual language invented. `Button`'s own `icon` prop was also unusable here regardless (it only renders a LEADING icon; the design's "Export ⌄" label needs a trailing chevron).

**Unanticipated addition -- a bundled, subsetted "Noto Sans" font (`apps/web/lib/fonts/noto-sans-subset.ts` + `NotoSans-OFL.txt`), embedded into every PDF export.** Not in the Code Map at all; found during this story's own live-verification step (Tasks list item 4), not anticipated at spec time. jsPDF's built-in "standard 14" fonts (Helvetica/Times/Courier) use WinAnsiEncoding, a single-byte Windows code page that predates Unicode 6.0 (2010) -- the version that added the Indian Rupee sign (₹, U+20B9). Rendering a real PDF with the pre-fix code and converting it to a PNG (`pdftoppm`) showed every Amount cell's "₹" mis-rendered as a stray, unrelated "¹" glyph -- a real, visually-confirmed defect affecting literally every PDF export (every Amount cell goes through `formatAmount()`, which always produces "₹..."), not an edge case. This directly threatens the AC's "matches exactly what was shown on screen" for the PDF format specifically (the Excel/OOXML path was never affected -- XML text has no such glyph-encoding limitation).

Fix: embedded a real, subsetted TrueType font via jsPDF's `addFileToVFS`/`addFont`. Sourced from Google's official "Noto Sans" variable font (`google/fonts` GitHub repo, SIL Open Font License 1.1 -- full license text copied to `apps/web/lib/fonts/NotoSans-OFL.txt`, since the OFL requires it travel with the font). Pinned to its default instance (`wght=400, wdth=100`, "Regular") via `fonttools.varLib.instancer`, then subsetted via `fonttools.subset` to Basic Latin + Latin-1 Supplement + Latin Extended-A/B/Additional/C/D + General Punctuation + Currency Symbols (covers ₹ plus €/£/¥) -- broad enough for arbitrary user-entered Person/Project/Notes text (e.g. accented names), deliberately not narrowed to only the literal characters this story's own fixtures use. Final embedded asset: ~139KB TTF (~186KB as the base64 TS constant) -- down from a ~2MB source variable font. Dynamically imported inside `exportReportToPdf` only (alongside `jspdf`/`jspdf-autotable`), never at module top level, extending Decision #4's "keep heavy export-only code out of the initial bundle" rule from the 3 named libraries to this font asset for the identical reason. No separate bold weight is bundled -- "bold" is registered pointing at the same regular-weight file, trading away the header row's visual boldness for guaranteed ₹-capable rendering everywhere (avoids `jspdf-autotable` silently falling back to a ₹-incapable default font when it can't resolve a "bold" variant, which is what happened during testing before this was added). A regression test (`report-export.test.ts`, "embeds the NotoSans font...") asserts the generated PDF's own raw byte stream contains the embedded font's name and a `/Subtype /CIDFontType2` or `/Type0` marker, since this test environment has no headless PDF renderer to assert on rendered glyphs directly.

**Dependency versions pinned (`apps/web/package.json`):** `exceljs@^4.4.0`, `jspdf@^4.2.1`, `jspdf-autotable@^5.0.8`.

**`pnpm audit` -- one real finding, fixed via an override, mirroring the `esbuild`/`drizzle-kit` precedent:** `exceljs@4.4.0` pins `uuid@^8.3.0` transitively, which resolved to a version with a moderate, already-patched finding (GHSA-w5hq-g745-h8pq, "missing buffer bounds check in v3/v5/v6 when `buf` is provided" -- `exceljs` only calls `uuidv4()` with no arguments, so this specific code path was never actually reachable, but the finding still trips the unconditional `pnpm audit` gate). Fixed with a `pnpm-workspace.yaml` override, `uuid@<11.1.1: ">=11.1.1"` -- `uuid`'s `v4()` call shape is unchanged v8 through v11, so this is a safe forward-pin, not a behavior change. Final `pnpm audit`: **zero vulnerabilities.** Also: `pnpm install` flagged a new transitive dependency, `core-js` (via `jspdf`'s optional `canvg` SVG-to-canvas dependency, unused by this story's table-only PDF export) needing a build-script approval decision -- set to `false` in `pnpm-workspace.yaml`'s `allowBuilds` (its postinstall only prints a donation banner; nothing this codebase needs to run).

**Live verification (2026-09-25):** Ran the full `pnpm turbo run test lint typecheck build --force --concurrency=1` and `pnpm lint:boundaries` -- both clean (`@niveshbook/core` 753 tests, `@niveshbook/db` 254 tests, `@niveshbook/web` 866 tests, all passing; 0 dependency-cruiser violations). `pnpm audit`: zero vulnerabilities.

Could not drive a real authenticated browser session end-to-end in this environment (no running dev server + seeded Postgres + browser automation set up for this pass) -- being explicit about that rather than silently skipping the requirement. What WAS actually verified, with real files, not mocks:
- `report-export.test.ts` (17 tests, post-review-round-1 -- see Review Triage Log): every one of the 6 report families' exact header/cell content asserted TWICE over -- once against a REAL `exceljs` round-trip (the `Blob` `exportReportToExcel` produces is re-opened with a FRESH `ExcelJS.Workbook` and its cells read back), and once against the exact `head`/`body` arguments the real `jspdf-autotable` call receives (captured via a `vi.mock` pass-through that still delegates to the real implementation) -- for `money-history` (incl. a cancelled entry with `" — Cancelled"` suffix, a cancelled+reversed entry with `" — Cancelled (reversal)"`, and a `null`-field `"—"` fallback case), `payment-mode`, `project-money`, `partner` and `sub-partner` (both incl. the `"33.3300"`/`"20.0000"` -> `"33.33%"`/`"20%"` Postgres round-trip trim, each family's OWN copy of `formatSharePercent` exercised through its actual trim regex, not just its no-op early-return path), and `available-balance`. A "filtered subset" test (both formats) proves export contains only the rows it's given, never more. Two NotoSans-font regression tests: one proving the font is embedded in the PDF at all, and a second, narrower one proving it's applied via the table-WIDE `styles.font` (not scoped to `headStyles` only) -- empirically confirmed this second test actually catches a headStyles-only regression that the first test alone would miss (verified by temporarily reintroducing that exact regression against the real code, observing the second test fail while the first kept passing, then reverting).
- A separate, temporary (not committed) live-verification script additionally wrote REAL `.xlsx`/`.pdf` files to disk (`/tmp/niveshbook-story-5-8-live-verify/`) for one entry-based type (`money-added`, 2 of 3 conceptual rows passed -- simulating a date-filter already having narrowed `state.rows` before export is ever called) and one aggregate type (`project-money`, 1 filtered row). The `.xlsx` files were independently re-opened with a fresh `ExcelJS.Workbook.readFile()` (proving the on-disk bytes, not just the in-memory buffer, are a valid OOXML workbook -- confirmed via `unzip -l`, a genuine `[Content_Types].xml`/`sharedStrings.xml`/`worksheets/sheet1.xml` structure). The `.pdf` files were independently verified three ways: `pdffonts` (confirms `NotoSans` is embedded as a `CID TrueType`/`Identity-H` font, not just referenced), `pdftotext -layout` (extracted text matches the filtered rows' content exactly, including the correct "₹" glyph and the em-dash cancellation suffix), and `pdftoppm` rendering to PNG for a direct visual read (confirmed by eye -- this is how the pre-fix "¹" defect was originally caught, and how the post-fix correct "₹" rendering was confirmed).
- `app/(dashboard)/reports/[type]/page.test.tsx` (+5 tests): the Export dropdown is disabled while loading, disabled on zero rows, disabled on an error state, and -- when enabled -- clicking "Export as Excel"/"Export as PDF" calls `exportReportToExcel`/`exportReportToPdf` with exactly the current `slug` and the exact `state.rows` array the page is holding (never a re-fetch), using `@testing-library/user-event` to drive the real Radix dropdown open/click interaction.

**Known limitation, disclosed:** the embedded font has no bold weight (see Deviation/addition above) -- PDF export header rows render in the same weight as body rows, unlike the on-screen table's bold column headers. This is a font-asset-size tradeoff, not a content-correctness gap (every AC-relevant property -- row/column content, money formatting, the "—" fallback, the cancellation suffix -- is unaffected), and was a judgment call given this story's scope; revisiting it (e.g. bundling a second bold-weight subset) is a reasonable follow-up if the visual mismatch matters in practice.

Fixed: added a second, narrower test asserting directly on the real `jspdf-autotable` call's actual `options.styles.font` (captured via a new `vi.mock("jspdf-autotable", ...)` pass-through that still delegates to the real implementation, since a plain `vi.spyOn` on an ESM module's `default` export isn't legal -- module namespace objects aren't configurable). 3. **[Applied, Low]** PDF header/body content was only asserted (via blob well-formedness alone, not real content) for 2 of the 6 report families; the other 4 (`payment-mode`, `partner`, `sub-partner`, `available-balance`) had no PDF-side content test at all. Also strengthened the 2 pre-existing "well-formed blob" tests (money-history, project-money) with the same `head`/`body` assertions, and added a PDF-side "filtered subset" test mirroring the Excel-side one, so all 6 families now have real content verification on both formats.
