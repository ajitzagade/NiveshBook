## Intent

**Problem:** A Sub-partner (linked via `subpartner_shares.userId`, Story 2.4) has no way to see even their own Sub-partner Share — the only existing read endpoint (`GET .../partner-shares/[partnerId]/subpartner-shares`) is scoped to Owner/Admin or the *parent Partner* (Story 2.4), never the Sub-partner themselves. Today a `sub_partner`-role login can authenticate but reach nothing.

**Approach:** Add a `GET` handler to the existing `apps/web/app/api/projects/[id]/partner-shares/[partnerId]/subpartner-shares/[subPartnerId]/route.ts` (currently `PATCH`-only) that returns a single Sub-partner Share row — allowed for Owner/Admin unconditionally, or the specific linked Sub-partner viewing their own row (`subpartner_shares.userId` matches the session), 403 for anyone else including a different Sub-partner or the parent Partner. Extends `packages/core/src/authorize.ts` with one new self-access action (`subpartner_shares:view`), reusing the exact `SELF_ACCESS_ACTIONS`/`ResourceRef.ownerId` mechanism Story 2.4 already established — no new mechanism invented.

**Decisions (resolved 2026-09-24):**
- **Single-resource GET, not a self-service "list my shares" endpoint.** AC2's explicit "via URL/ID manipulation... same gate extension as Story 2.4, applied to Sub-partner-scoped `resourceRef`s" names a single-resource, ownership-gated check — the direct one-level-deeper analog of Story 2.4's `subpartner_shares:list` self-access (`ResourceRef.ownerId` matching `partner.userId`) now matching `ResourceRef.ownerId` against the target row's own `userId`. A project-agnostic "list everything I'm linked to" endpoint isn't what the AC describes and isn't built here.
- **Discoverability (how a Sub-partner learns their own `id`/`partnerId`/`subPartnerId` to call this) is explicitly out of scope**, mirroring Story 2.4's identical "dashboard shell stays Owner/Admin-only, discoverability is a later UI concern" Decision — now doubly confirmed: `epics.md`'s Epic 5 roadmap has a dedicated later story, **5.6 "Sub-partner dashboard"**, for the actual self-service UI. This story ships only the verified API contract, tested the same way every other story's "direct URL/ID manipulation" AC has been tested throughout Epic 2 (a known, hand-typed URL).
- **Closing Story 2.4's own review lesson, by design this time, not by a later patch:** resolving path-segment existence (project/partnerId/subPartnerId scoping) before deciding 404-vs-403 would let *any* authenticated caller — not just an authorized one — use this endpoint as an existence oracle, exactly the bug Story 2.4 shipped and had to patch. This route avoids it structurally: resolution happens once regardless of caller, but the *response* differs by caller — Owner/Admin gets the existing granular 404 semantics (matches every other Owner/Admin route's precedent); anyone who is not Owner/Admin and not the matching Sub-partner gets a single uniform 403 for every failure mode (malformed id, nonexistent, wrong-scope, or exists-but-not-theirs) — never a 404, so no unauthorized caller can distinguish "doesn't exist" from "not yours."
- **The parent Partner does not get single-detail access via this new route.** They already have full list access to all their own Sub-partners via the pre-existing `GET .../subpartner-shares` (Stories 2.3/2.4) — a redundant single-detail grant here isn't required by any AC and adds an unnecessary second `ResourceRef.ownerId` to check. Not required, not built.
- **`PATCH` (edit) is unchanged — still Owner/Admin-only.** This story's AC is entirely about *viewing*; nothing asks for Sub-partner self-service editing (mirrors Story 2.4's identical write-stays-admin-only Decision).
- **No new schema, no new port method, no new client-side fetch helper.** The new `GET` reuses the exact `findLatestByPartnerId`/`findLatestBySubPartnerId` port calls `PATCH` already uses in this same file — no new query shape. No UI consumes this endpoint yet (Story 5.6 is the first consumer, and can add its own fetch helper alongside whatever UI it builds) — building one now would be dead code with no caller.

## Boundaries & Constraints

**Always:** `GET .../subpartner-shares/[subPartnerId]` requires a valid session (401 if none). Resolution (project exists, `partnerId` belongs to it, `subPartnerId` belongs to `partnerId`) runs the same way for every caller, mirroring `PATCH`'s existing chain exactly (no new validation shape). Once resolved: Owner/Admin always gets `200` with the row. The specific linked Sub-partner (`subShare.userId === session.userId`, case-insensitive, matching `authorize()`'s existing self-access idiom) gets `200` with their own row. Everyone else — a different Sub-partner, the parent Partner, an unrelated Partner, a `sub_partner` whose own userId doesn't match this row — gets a uniform `403 {code: "forbidden"}`, identical for a resolution failure (malformed/nonexistent/wrong-scope path segments) and a resolution success where ownership just doesn't match. Only Owner/Admin ever receives the granular 404 for a resolution failure.

**Never:** No change to `PATCH`'s existing Owner/Admin-only gate. No single-detail access for the parent Partner via this new route. No new `/api/me/...`-style self-service endpoint. No UI, no client-side fetch helper, no schema change, no new port method. No change to any other existing route in this file or elsewhere in the epic.

## Code Map

- `packages/core/src/authorize.ts` — add `"subpartner_shares:view"` to the `Action` union; add `PERMISSIONS["subpartner_shares:view"] = new Set(["owner_admin"])`; add `"subpartner_shares:view"` to `SELF_ACCESS_ACTIONS` (reuses `authorize()`'s existing `ResourceRef.ownerId` self-access check unchanged — zero new logic in `authorize()` itself, purely additive constant entries, exactly mirroring Story 2.4's `subpartner_shares:list` addition).
- `apps/web/app/api/projects/[id]/partner-shares/[partnerId]/subpartner-shares/[subPartnerId]/route.ts` — add `GET`, alongside the existing `PATCH`. Resolves path segments via the same chain `PATCH` already uses (`isValidProjectId`/`isValidPartnerId`/`isValidSubPartnerId` format checks, `findLatestByPartnerId` + `partner.projectId === id`, `findLatestBySubPartnerId` + `existing.partnerId === partnerId`). On any resolution failure: look up the actor's role (`userPort.findUserById`) — Owner/Admin gets the existing granular 404 (`subPartnerShareNotFoundResponse()`/`partnerShareNotFoundResponse()`, matching `PATCH`'s precedent); anyone else gets a uniform 403. On resolution success: call `authorize(session.userId, "subpartner_shares:view", { ownerId: subShare.userId ?? "" }, { users: userPort })` — `200` with the row if allowed, uniform 403 otherwise.
- Test file (same directory, `[subPartnerId]/route.test.ts`) — add `describe("GET .../subpartner-shares/[subPartnerId]")` covering every I/O matrix row above, explicitly including a non-Owner/Admin caller (a Sub-partner not matching, and a `partner`-role caller) hitting a malformed/nonexistent path segment and asserting uniform 403 — the exact regression class Story 2.4 shipped and had to patch, now tested from the start.

- `apps/web/app/api/projects/[id]/partner-shares/[partnerId]/subpartner-shares/[subPartnerId]/route.ts`: added `GET` alongside the existing `PATCH`, reusing the exact same `findLatestByPartnerId`/`findLatestBySubPartnerId` resolution chain. A `resolutionFailed()` helper re-reads the actor's live role via `userPort.findUserById` on any resolution failure — Owner/Admin gets `subPartnerShareNotFoundResponse()` (`PATCH`'s own precedent, which uses that single 404 response for every resolution-failure stage, not a separate `partnerShareNotFoundResponse()`); anyone else gets the same uniform 403 used when resolution succeeds but `authorize("subpartner_shares:view", ...)` denies on ownership mismatch — so no unauthorized caller can distinguish "doesn't exist" from "not yours," closing Story 2.4's own shipped-then-patched review lesson structurally instead of retroactively. `route.test.ts` adds a `describe("GET .../subpartner-shares/[subPartnerId] (Story 2.5)")` block covering every I/O matrix row, including a `sub_partner` and a `partner` caller each hitting a malformed/nonexistent path segment and asserting 403 (not 404).
