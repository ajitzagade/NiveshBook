## Intent

**Problem:** FR27 requires every withdrawal's actual destination captured — split across another Project, a Person, Available Balance, and/or Other — reconciled to the exact withdrawn amount, in one atomic action. No allocation infrastructure exists yet.

**Approach:** New `withdrawal_destination_allocations` table (one row per destination leg), written atomically (one DB transaction + one `audit_log` row per AD-5) immediately after Take Now succeeds — the "Where did this money go?" prompt is the next step in the *same* flow (epic-4-context.md), not a separate later screen. Two of the four destination types have their real downstream effects built by later stories: a "Project" leg is just recorded here (`destinationProjectId` + `amount`) — Story 4.8's `moveWithdrawalToProject()` is what actually creates the linked money-movement/investment record, per AD-6 ("accepts and participates in a caller-supplied transaction... so FR-27's multi-destination split... commits or rolls back as a single unit"); an "Available Balance" leg is likewise just recorded — Story 4.9's ledger is what actually credits it. This story builds the data-capture, validation, and atomic-write foundation both later stories extend, not their effects.

**Decisions (resolved 2026-09-25) — "Person"/"Other" are genuinely undefined in the PRD/epics/UX docs (confirmed absent by investigation); resolved as the only options unblocked by current infrastructure:**
- **"Person" destination is a free-text name field.** No Person/contact entity exists anywhere in the schema, and none is specified — building one would be unaddressed scope creep. `personName: text, nullable`, set only when `destinationType: "person"`.
- **"Other" destination is a free-text description field**, same reasoning. `notes: text, nullable` (also usable as a general notes field on any leg).
- **Allocation is write-once per withdrawal, not editable/re-enterable.** No AC/FR addresses re-splitting an already-allocated withdrawal; epic-4-context.md frames the prompt as "the very next step in the same flow," implying a single pass. Enforced by a precondition check (reject with 409 if any allocation rows already exist for this `withdrawalTransactionId`) — mirrors this codebase's anti-speculative-building principle (Story 3.3's "no status/cancel column until Story 3.8 actually needs it") rather than building an edit capability no story asks for. Story 4.11's cancel/reverse (the whole withdrawal + its bundle) remains the only undo path.
- **Owner/Admin-only, no self-access.** The AC's persona is "As an Owner/Admin," with no "(or the withdrawal's own Partner/Sub-partner)" qualifier — unlike Story 4.2's Take Now AC, which has exactly that qualifier and got self-access. Mirrors Story 3.1/3.7/3.8's identical AC-persona-driven precedent.
- **A "Project" destination excludes the source Project itself** ("another Project" — moving money to the same project it came from isn't a destination). Enforced as a 400 validation error, not silently allowed.
- **`withdrawal_destination_allocations` carries its own `idempotencyKey`, one shared value across every leg of one save** (not per-row) — mirrors AD-5's multi-record atomic-write precedent (Story 3.8's cancel/reversal pair). A replay with the same key and matching total returns the original rows; a genuine collision (different content, same key) is rejected, mirroring `WithdrawalIdempotencyKeyConflictError`'s exact precedent.

## Boundaries & Constraints

**Always:** `POST /api/projects/[id]/withdrawal-transactions/[transactionId]/destination-allocations` requires a valid session (401) and `authorizeScope()`/`authorize()` for a new `"withdrawal_destination_allocations:create"` action (Owner/Admin-only, no self-access). The target withdrawal transaction is resolved first (404 if missing or belongs to a different Project). Allocated amounts are validated to sum to *exactly* the withdrawal's `amount` (400 if not, before any write). Every successful save writes all destination-leg rows plus one `audit_log` row in a single DB transaction (AD-5/AD-6) — never partial. A "project" leg's `destinationProjectId` is validated to exist and differ from the source Project (400 otherwise). Rejects with 409 if the target withdrawal already has allocation rows.

**Never:** No creation of the actual linked money-movement/investment record for a "project" leg (Story 4.8's job) — this story only records the raw allocation. No Available Balance ledger credit (Story 4.9's job, table doesn't exist yet). No edit/re-allocation of an already-allocated withdrawal. No self-access — Owner/Admin only.

## I/O & Edge-Case Matrix

| Scenario | Input / State | Expected Output / Behavior | Error Handling |
|----------|--------------|---------------------------|----------------|
| Exact multi-destination split (AC1) | ₹2,50,000 withdrawal; legs: ₹1,50,000→Project B, ₹50,000→Person X, ₹50,000→Available Balance | 201, 3 rows saved atomically | N/A |
| Amounts don't sum to withdrawal total | Legs sum to ₹2,00,000 against a ₹2,50,000 withdrawal | Rejected before any write | `400 allocation_mismatch` |
| Amounts sum to more than withdrawn | Legs sum to ₹3,00,000 against a ₹2,50,000 withdrawal | Rejected | `400 allocation_mismatch` |
| Project leg targets the source Project itself | `destinationProjectId` === the withdrawal's own `projectId` | Rejected | `400 validation_error` |
| Project leg targets a nonexistent Project | Malformed/missing `destinationProjectId` | Rejected | `400 validation_error` |
| Already-allocated withdrawal | A second allocation attempt for the same `transactionId` | Rejected | `409 already_allocated` |
| Duplicate submission, same `idempotencyKey`, identical content | Two concurrent `POST`s | Exactly one set of rows created; both return the same rows (200 on replay) | N/A |
| Same `idempotencyKey`, mismatched content | Different total/legs, same key | Rejected | `409 idempotency_key_conflict` |
| Non-Owner/Admin attempts allocation | Any Partner/Sub-partner session, even the withdrawal's own | 403 | `{code: "forbidden"}` |
| Nonexistent/malformed `transactionId` | Any caller | 404 | `{code: "not_found"}` |
| Single destination for the full amount | One leg, "other" type, full amount | 201 | N/A |

**Acceptance Criteria (from epics.md Story 4.7):**
- Given a ₹2,50,000 withdrawal by Partner A, when Owner/Admin allocates ₹1,50,000 → Project B, ₹50,000 → Person X, ₹50,000 → Available Balance, then the form shows "Distributed: ₹2,50,000 / ₹2,50,000 ✓" and allows saving.
- Given a partial allocation that doesn't sum to the withdrawn amount, when save is attempted, then it's blocked until the amounts reconcile exactly.
- Given the save is processed, when it commits, then all destination legs commit or roll back together as one transaction (AD-6) — no partial allocation is ever left behind.

## Spec Change Log

Patch round 1 (Review Triage Log rows 1-3, 7, 16): fixed a critical bug where the destination-allocation dialog's default, unedited state (one "other" leg, full amount, blank notes) always failed server validation — Save appeared enabled (the sum-only gate) but always 400'd on submit, breaking the single most common path through the feature. Added client-side per-leg completeness validation (`isAllocationLegComplete`) mirroring the server's `isValidLeg` rules, so Save now stays correctly disabled until every leg's type-specific field is filled in. Also: added UUID-shape validation on `destinationProjectId` before the DB lookup (was risking an unhandled 500 on malformed input); reordered the already-allocated (409) check to run before exact-sum validation, so a resubmission against an already-allocated withdrawal gets 409 even with an also-invalid total; disambiguated `aria-label`s across multiple destination rows; added a visible error state for a failed Projects fetch. Independently re-verified: `pnpm turbo run test lint typecheck build --force --concurrency=1` (18/18 green, 569 web tests — serial execution used to route around the already-tracked, unrelated `withdrawal-transaction-port.test.ts` flake under parallel `turbo run`, see `deferred-work.md`), `pnpm lint:boundaries` (clean, 238 modules/431 deps).
