## Intent

**Problem:** FR-41/FR-42 ask for a viewing surface over the `audit_log` rows already written for every investment/withdrawal transaction edit and cancel (AD-5, Stories 3.3/3.7/3.8/4.2/4.11) — visible to Owner/Admin generally, and to a transaction's own Partner/Sub-partner for that transaction specifically. Investigation found this is NOT a pure "add a viewing UI over already-complete data" story: `WithdrawalTransactionPort` has no `findAuditLogByTransactionId` method and no route exists for it at all — despite Story 4.11 already writing `entityType: "withdrawal_transaction"` rows — a gap `packages/db/src/ports.ts:999`'s own doc comment explicitly calls "Story 4.11's job," left undone. This story must close that read gap before it can build the viewing surface epics.md's AC actually asks for.

**Approach:** Confirmed with the user 2026-09-26:
1. **Scope is transaction-audit only, matching the AC's literal text** ("a transaction edited in Story 3.7 or 4.11," named twice). Three OTHER long-standing "no audit trail" gaps already logged in `deferred-work.md` — user activate/deactivate (Story 1.6), permission grant/revoke (Story 1.7), Project create/edit (Story 2.1) — stay deferred, unchanged. This story adds no new audit-*writing* code for any of them; only investment/withdrawal transaction audit data (already written) is read/surfaced here.
2. **`available_balances` pool mutation history stays deferred too.** `deferred-work.md`'s existing entry for this explicitly left the call to "whether Story 5.9's own scope covers it" — it doesn't; closing it needs a new append-only ledger table (real new schema, that entry's own words: "not a one-route patch"), out of proportion with this "viewing surface" story. The deferred-work.md entry is updated to record this decision, not left ambiguous.
3. **Partner/Sub-partner self-access is a per-transaction entry point, NOT a nav item.** The main "Audit History" nav item (new — no placeholder exists today, unlike Reports' pre-built inert entry) is Owner/Admin-only, matching `EXPERIENCE.md`'s IA table and the precedent already set by Stories 5.5/5.6 (which both already list "Audit History" among items staying hidden for `partner`/`sub_partner`). A transaction's own Partner/Sub-partner instead gets a "View Audit History" link/action next to their own transaction rows (Add Money/Withdraw Money pages) — this fully satisfies FR-41's "visible to ... the transaction's own Partner/Sub-partner" consequence and AC clause 3's literal self-access/403 requirement, without widening the dashboard shell (a separate, higher-stakes decision this story doesn't need to make).
4. **Close the withdrawal-transaction audit read gap first**, mirroring the existing investment-transaction shape exactly: `WithdrawalTransactionPort.findAuditLogByTransactionId()`, a `listAuditLogForTransaction()` core wrapper, a new `withdrawal_transactions:view_audit` `authorize.ts` action (owner_admin unrestricted + self-access via `SELF_ACCESS_ACTIONS`, byte-for-byte mirroring `investment_transactions:view_audit`'s existing shape), and a new nested route `GET .../withdrawal-transactions/[transactionId]/audit-log`, mirroring the existing investment route's exact structure (session → resource-existence chain → target-share resolution → `authorize()` → response).
5. **"Cancelled/reversed pairs shown linked" (AC clause 2) is resolved via `reversalOfTransactionId`** (an existing, indexed, self-referencing column on both `investment_transactions`/`withdrawal_transactions`, Stories 3.8/4.11) — NOT via anything new on the `audit_log` table itself (which has no such column). BOTH the per-transaction audit routes (investment, existing; withdrawal, new) are extended to also resolve and return the linked transaction (the reversal, if the requested transaction has one; the original, if the requested transaction IS a reversal) plus that linked transaction's own audit entries — one mechanism, reused identically by both Owner/Admin's drill-down and Partner/Sub-partner's self-access view, since both go through the same route.
6. **A new Owner/Admin-only global Audit History page** (`/audit-history`), listing every `audit_log` row whose `entityType` is `investment_transaction` or `withdrawal_transaction` (matching Decision #1's scope — the `audit_log` table's other 3 already-written entity types, `withdrawal_destination_allocation`/`available_balance_spend`/`adjustment_netting`, stay unexposed by this story, logged as a new `deferred-work.md` item rather than silently expanded into). A new narrow `AuditLogPort.listAll()` (Interface Segregation — a new port, not widening either transaction port) plus a new pure `assembleAuditHistory()` (`packages/core`) resolve each row's actor name and cross-reference `reversalOfTransactionId` (reusing the already-fetched `investment_transactions`/`withdrawal_transactions` `listAll()` data — no new query shape) so a cancel-entry and its reversal-creation-entry can be visually grouped/linked on this list too, the same property as Decision #5, applied system-wide instead of per-transaction.
7. **No new pagination/filtering infrastructure is required by this story's own AC** (unlike Story 5.7's FR-39) — the global page may grow slowly unbounded over time as more transactions are edited/cancelled; if/when that becomes a real performance problem, it's a follow-up story's job (log a fresh `deferred-work.md` entry rather than build speculative pagination now).

## Boundaries & Constraints

**Always:** Every `audit_log` write path (Stories 3.3/3.7/3.8/4.2/4.11) stays completely unchanged — this story is READ-ONLY over that table. `authorize()`'s existing `investment_transactions:view_audit` shape is mirrored exactly for the new `withdrawal_transactions:view_audit` action — same two-tier grant (owner_admin unrestricted + `SELF_ACCESS_ACTIONS` self-access), never a broader or narrower grant invented for this story. The existing investment audit-log route's response shape (`{ entries }`) is extended additively (a new `linkedTransactionId`/`linkedEntries` field), never replaced — confirmed no existing UI consumer of that route exists yet, so this is the first and only consumer, but the addition is still additive by convention, not a breaking reshape.

**Never:** No new audit-*writing* code for user deactivation, permission grants, or Project edits (Decision #1 — those stay deferred, unchanged). No `available_balances` pool mutation ledger (Decision #2 — stays deferred, unchanged). No widening of the main nav's Owner/Admin-only Audit History item to `partner`/`sub_partner` (Decision #3). No exposure of `withdrawal_destination_allocation`/`available_balance_spend`/`adjustment_netting` audit rows on the new global page (Decision #6 — out of scope, logged as future deferred work if ever needed).

## Implementation Notes

**Followed the Code Map's overall shape closely, with a few deliberate, documented deviations:**

**Deviation #1 — added `findByReversalOfTransactionId` to BOTH `InvestmentTransactionPort` and `WithdrawalTransactionPort`, not just implied by the Code Map's prose.** The Code Map's investment-route bullet says the linked-reversal resolution needs "one extra `findById`-shaped lookup" but doesn't name a method; there was no existing port-level way to ask "does transaction X have a reversal" (only `packages/db`'s own private `findReversalRow`/`findWithdrawalReversalRow` helpers, internal to `ports.ts`). Rather than have the route reach past the port abstraction, added `findByReversalOfTransactionId(originalTransactionId): Promise<T | null>` to both port interfaces, implemented as thin public wrappers over the existing private helpers (no new query shape, no behavior change to any existing write path). This keeps AD-9 intact (route never touches Drizzle directly) and mirrors this codebase's established "one method per real access pattern" port design.

**Deviation #2 — the new withdrawal-side core wrapper is named `listAuditLogForWithdrawalTransaction`, not `listAuditLogForTransaction` (which the Code Map's prose uses verbatim).** `investment-transaction.ts` already exports `listAuditLogForTransaction`; `packages/core/src/index.ts`'s two `export *` statements can't both export a value under the same name (this codebase's own established, already-documented precedent for this exact collision class — `InvalidWithdrawalAmountError`/`WithdrawalShareNotFoundError`/etc. in `withdrawal-transaction.ts`, each renamed for the identical reason). Named consistently with that file's own "Withdrawal"-prefixed convention.

**Deviation #3 — `AuditHistoryRow.linkedTransactionId` (the global page's assemble function) tags EVERY entry belonging to a since-reversed transaction, not just its `"cancel"` action row.** The tag is keyed on `entityId` (the transaction), not on `action` — a transaction that's been cancelled has its whole trail (its original `"create"` entry too) shown as linked/reversed, not just the cancel moment. This reads more usefully on the global page (grouping is visually about "this transaction's story," not one single row) and is simpler to implement (`Map<entityId, reversalId>` applied to every row via a single lookup) than conditioning on `action === "cancel"`. The per-transaction audit-log routes' own `linkedTransactionId`/`linkedEntries` (transaction-scoped, not row-scoped) are unaffected by this — that mechanism resolves one linked transaction per REQUEST, independent of this row-tagging choice.

**Deviation #4 — `AuditHistoryRow.actorName` resolves to the actor's `email`, not a "name."** `User` (`packages/types`) has no `name` field (only Partner/Sub-partner Shares do) — email is the only available human-readable identifier for `audit_log.actorUserId`, which is always a `users.id`, never a Partner/Sub-partner Share id.

**Deviation #5 (post-review fix — see the Spec Change Log entry above for the full story) — added a new flat investment audit-log route, `GET /api/projects/[id]/investment-transactions/[transactionId]/audit-log`, alongside (not replacing) the original nested one.** The self-access "View Audit History" action moved from Add Money/Withdraw Money (unreachable by Partner/Sub-partner) to the Money History page, whose `MoneyHistoryEntry` rows never carry a `requirementId` the nested route needs. The nested route (Story 3.7) is untouched and still fully tested — just no longer called by any page.

**Judgment calls the Code Map left open:**

- The "View Audit History" dialog's own layout (`AuditHistoryEntries`/`AuditHistoryEntryList`): a plain list of Action/Date/Reason per entry, with a "Linked Transaction (id)" section shown only when `linkedTransactionId` is non-null. Post-review fix: this now lives solely on the Money History page (`money-history/page.tsx`) as an "Audit" column action shown only for `"money_added"`/`"money_withdrawn"` rows — the original per-page copies on Add Money/Withdraw Money were removed once the entry point moved (see Spec Change Log).

- "View Audit History" is shown for EVERY auditable row regardless of `status` (unlike Edit/Cancel, which hide once `status === "cancelled"`) — viewing the audit trail of an already-cancelled row (or navigating to a reversal row's own audit trail) is exactly the point, never something to hide.

**Two correctness properties worth calling out explicitly (both covered by tests, per this story's own "Specific correctness properties" list):**
1. **Reversal transactions never get their own `audit_log` row.** `cancelTransaction`'s atomicity contract (Stories 3.8/4.11, unchanged by this story) writes exactly one `"cancel"` `audit_log` entry, against the ORIGINAL transaction's id — the newly-created reversal row itself is never the `entityId` of any `audit_log` row. This means `findAuditLogByTransactionId(reversalId)` always returns `[]`. Both audit-log routes' `linkedEntries` correctly surface this as an empty array (not a bug, not a missing case) when navigating FROM the original TO the reversal; navigating the other way (from the reversal to the original) returns the full trail as `linkedEntries` instead. Verified with a real cancelled-transaction-plus-reversal fixture, both directions, in `packages/core/src/withdrawal-transaction.test.ts`, `packages/db/src/audit-log-port.test.ts` (live Postgres), and both audit-log route test files.
2. **Case-insensitive self-access matching** was already correct on the investment side (confirmed by reading `authorize()`'s existing implementation, not assumed) and is mirrored byte-for-byte for `withdrawal_transactions:view_audit` (same `SELF_ACCESS_ACTIONS` set, same `authorize()` function, no new comparison logic needed).

Post-review fix: a mirroring live-Postgres `describe` block was added for `createInvestmentTransactionPort`'s identical two methods (previously only mock-covered — a real gap this fix closed, see the Spec Change Log entry above), exercising the identical cancel+reversal fixture against the investment ledger. ## Spec Change Log

**2026-09-26, post-review, Decision #3's self-access entry point relocated from Add Money/Withdraw Money to Money History:**

**What was wrong:** Decision #3 (frozen Intent, above) says the Partner/Sub-partner self-access "View Audit History" entry point is "a per-transaction entry point, NOT a nav item... next to their own transaction rows (Add Money/Withdraw Money pages)." This was written without checking whether a Partner/Sub-partner can actually reach those two pages — they can't. Three independent, pre-existing (not touched by this story) gates all block it: (1) `apps/web/app/(dashboard)/layout.tsx`'s `addMoney`/`withdrawMoney` nav items are `OWNER_ADMIN_ONLY`, so a Partner/Sub-partner never even sees a link to either page; (2) `apps/web/app/(dashboard)/projects/layout.tsx` (Story 5.5) wraps the entire `/projects/**` subtree in `requireOwnerAdminSession()`, so a non-owner_admin session hitting either page directly by URL redirects to `/` before the page renders; (3) `investment_transactions:list`/`withdrawal_transactions:list` (`authorize.ts`) are `owner_admin`-only with no `SELF_ACCESS_ACTIONS` entry, so even the transaction-list calls populating those pages would 403 for a Partner/Sub-partner regardless. Net effect: AC clause 3 (self-access + 403-for-others) was undeliverable through the shipped UI, even though the underlying per-transaction audit-log routes' own self-access logic was, and remains, correct and fully tested — this was purely a UI-placement mistake in the frozen Intent, not a bug in the code built to it. Caught by an independent edge-case review pass, not self-discovered.

**What replaced it:** The self-access "View Audit History" action moved to the Money History page (`apps/web/app/(dashboard)/money-history/page.tsx`, Story 5.1) instead — genuinely reachable by all three roles (its nav item and the underlying `money_history:list` action already grant `owner_admin`/`partner`/`sub_partner`, and `resolveMoneyHistoryScope()` already scopes a Partner/Sub-partner to only their own rows). Shown only for a `"money_added"`/`"money_withdrawn"` `MoneyHistoryEntry` row (the two types whose `id` is a real, directly-queryable `investment_transactions`/`withdrawal_transactions` row id, per that type's own doc comment) — every other entry type (leg-derived from a withdrawal) stays out of scope for this fix. Routing snag resolved by adding a new flat investment audit-log route, `GET /api/projects/[id]/investment-transactions/[transactionId]/audit-log` (`apps/web/app/api/projects/[id]/investment-transactions/[transactionId]/audit-log/route.ts`), mirroring the withdrawal side's already-flat, `requirementId`-free shape — chosen over the alternative (resolving `requirementId` server-side so the caller never supplies it) because it needed no new resolution step at all: `investmentTransactionPort.findById(transactionId)` alone already fully validates and identifies the transaction, exactly like the withdrawal route already does. The original nested investment route (`.../investment-requirements/[requirementId]/transactions/[transactionId]/audit-log`, Story 3.7) is untouched and still fully functional/tested; it's simply no longer called by any page after this fix (kept for a possible future Owner/Admin per-requirement drill-down — see `apps/web/lib/investment-transactions.ts`'s `getAuditLog`'s own doc comment). "View Audit History" was removed entirely from Add Money/Withdraw Money (Owner/Admin already has full, system-wide access via the existing global `/audit-history` page, so keeping a duplicate, now-pointless action there for Owner/Admin's convenience wasn't worth the extra code path). `apps/web/app/(dashboard)/layout.tsx`'s `auditHistory` nav item's own doc comment is updated to point at Money History instead of Add Money/Withdraw Money.

**Correctness properties added by this fix:** every existing per-transaction audit-log route test, port test, and live-Postgres test is unaffected (the routes/ports themselves didn't change); new coverage: the flat investment route's own `route.test.ts` (mirroring the withdrawal route's test suite exactly), a live-Postgres `describe` block for `createInvestmentTransactionPort.findAuditLogByTransactionId`/`.findByReversalOfTransactionId` (`packages/db/src/audit-log-port.test.ts` — this method had ZERO real coverage anywhere before this fix, only mocks, a separate post-review finding), and `money-history/page.test.tsx`'s new "View Audit History action" describe block (shows/hides correctly by entry type, fetches via the correct route per type, renders a REAL non-empty linked-reversal section, doesn't trigger the row's own trace navigation on click, surfaces a fetch error inline).
