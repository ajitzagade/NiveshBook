## Intent

**Problem:** Story 5.10 was appended to Epic 5 on 2026-09-25 (no FR number, added per founder request after reviewing an external reference diagram not present in this repo) — two days after `EXPERIENCE.md`/`DESIGN.md` were finalized and three days after `ARCHITECTURE-SPINE.md`. Neither doc mentions this screen at all: no layout, no interaction pattern, no component precedent, and no charting/diagramming library exists anywhere in this codebase. Unlike Stories 5.7/5.8/5.9 (which extended an existing pattern one step further), this is a genuinely new visual paradigm with almost no prior art to anchor against — epics.md's own AC is unusually detailed for a late addition (5 full Given/When/Then blocks, explicit reuse pointers to real existing code), but the *presentation* is entirely undefined.

**Approach:** Confirmed with the user 2026-09-26:
1. **Rendering uses a dedicated diagramming library, `@xyflow/react`** (the actively-maintained successor package to the now-legacy `reactflow` name) — a new runtime dependency, subject to the same `pnpm audit` zero-vulnerability gate Story 5.8's `exceljs`/`jspdf` already went through. Nodes are custom-styled to match this codebase's existing token/Card visual language, not the library's default look. Node positions are computed deterministically from the tree structure (no user dragging/persisted layout — nobody asked for that); the library's own built-in pan/zoom may stay enabled (implementer's call) since it's free with the library and harmless, but is not itself an AC requirement.
2. **Three view modes, all reusing already-computed/already-stored data, per epics.md's own explicit mandate — zero new raw-data aggregation beyond one small, `reports.ts`-precedented exception (Decision #4):**
   - **Percentage** — a Partner's own `PartnerShare.sharePercent`, or (if they have current Sub-partners) their *retained* % = `sharePercent − sum(current Sub-partner sharePercent)`, exactly mirroring `shares/page.tsx`'s existing `retainedMessage`/`formatDifference` formula (duplicated locally per this codebase's established per-module convention, same as `formatSharePercent`). A Sub-partner's own node shows their own `sharePercent` (already "of the whole Project," per AD-3's data model — never re-derived).
   - **Actual Amount** — sum of `status: "active"` `investment_transactions.amount` for that `shareId` on that Project, via `sumMoney()`. This is the same underlying computation Story 3.4's `resolveAndUpsertAdjustment` itself performs internally (`sumMoney(transactionsByShareKey[...])`, `investment-adjustment.ts:77`) — reused as a technique, not by reading Story 3.4's stored `investment_adjustments.actualPaid` value directly, since that field is scoped to one funding-requirement round while this mode's "actual invested amount **to date**" is explicitly cumulative across a Project's full history (which may span several requirement rounds, Story 3.5). Mirrors the exact aggregation shape already proven 4 times over in Stories 5.4-5.7's dashboards/reports.
   - **Money Flow** — Total In (sum of active `money_added` amounts) and Total Out (sum of active `money_withdrawn` + `moved_to_project`-as-source amounts) per `shareId`, all-time, no date filter (epics.md's AC never asks for one, and its own text says "reusing existing trail data rather than a new computation" — a filtered view would need new filter-plumbing this AC doesn't request). This is the one genuinely new small aggregation this story adds: `packages/core/src/ownership-structure.ts`'s own `Map`-bucket-then-`sumMoney()`-reduce, mirroring `reports.ts`'s `assemblePaymentModeReport()` precedent exactly (a second-order pure function over already-fetched transaction data, not a new port or a change to `assembleMoneyHistory()`). Direction (in vs. out) is shown as two distinct labeled figures per node, not a single net number — the AC only asks the direction be "clearly indicated," and two explicit figures is the least-lossy, least-inventive way to satisfy that.
3. **Two new `authorize.ts` actions, mirroring Story 2.3/2.4's established co-partner-privacy-boundary precedent** (a Partner never sees another Partner's own structure or Sub-partner split): `ownership_structure:view_project` (`owner_admin`-only — the full, unscoped Project tree showing every Partner) and `ownership_structure:view_partner` (self-access via `SELF_ACCESS_ACTIONS` — `owner_admin` unrestricted, plus the target Partner's own linked `userId`, plus that Partner's own linked Sub-partners viewing their own even-narrower slice). A Partner/Sub-partner never reaches the unscoped project-wide view at all — their own entry point (Decision #5) always lands directly on their own already-scoped view.
4. **New top-level page, `apps/web/app/(dashboard)/structure/[projectId]/page.tsx`**, sibling to `money-history`/`reports`/`audit-history` — deliberately OUTSIDE `/projects/**` (confirmed: `apps/web/app/(dashboard)/projects/layout.tsx`'s `requireOwnerAdminSession()` gate, by Next.js App Router's own file-based nesting rules, only wraps `/projects/**` routes; a sibling top-level segment is structurally outside its reach). This is a direct, deliberate application of Story 5.9's own hard-learned lesson: that story's Partner/Sub-partner self-access entry point was originally placed on Add Money/Withdraw Money (both gated Owner/Admin-only by `projects/layout.tsx`) and was completely unreachable by the role it needed to serve, caught only in review. This story's page independently calls its own authorization check (mirroring Money History's/Audit History's established "own guard, not inherited from a nested layout" pattern) rather than repeating that exact mistake.
5. **Two distinct, role-appropriate entry points, no new nav item:** Owner/Admin reaches the full unscoped tree via a new "Structure" action on the Projects list page (`apps/web/app/(dashboard)/projects/page.tsx`), mirroring the existing Edit/Shares/Add Money/Withdraw Money button row's exact pattern, linking to `/structure/[projectId]` (no query param). A Partner/Sub-partner reaches their own scoped view via a new "View Structure" action on their own Home dashboard's already-existing "My Projects" list (`ShareRow`'s currently-unused `action` slot, Stories 5.5/5.6), linking to `/structure/[projectId]?partnerId=<their own partnerId>` (or `?subPartnerId=...`). No standalone top-level nav item is added — mirrors the existing Available Balance page's own precedent (reached only via a per-Project action, never its own nav entry).
6. **The Project-vs-Partner scope is a query param on the SAME page** (`?partnerId=X` / `?subPartnerId=X`, absent = full unscoped Project tree), not a separate route per drill level — clicking a Partner node in the full Owner/Admin view re-scopes the same page client-side (query-param update, no full navigation), with a "back to full Project" affordance to clear it. This mirrors AC block 2's own framing that switching modes/scope is "purely a display change," extended consistently to scope changes too.
7. **View-mode switching (Percentage/Actual Amount/Money Flow) is client-side-only state, never re-fetches or changes tree shape/scope** (AC block 2, frozen literally) — the page fetches the full tree (all 3 modes' worth of data) once per scope, and the toggle just picks which fields to render.
8. **Zero-Sub-partner and zero-Partner edge cases render gracefully, not as errors**: a Partner with no current Sub-partners renders as a leaf (Project→Partner, no second level); a Project with zero current Partner Shares renders an `EmptyState` (`packages/ui`), matching every other list screen's established convention.

## Boundaries & Constraints

**Always:** Every sum uses `sumMoney()` (AD-2). Only CURRENT Partner/Sub-partner Shares are considered (mirrors every existing current-shares convention). Only `status: "active"` transactions count toward Actual Amount/Money Flow (mirrors every existing active-only sum). `pnpm audit` must show zero vulnerabilities for `@xyflow/react` before this story merges (AGENTS.md's existing, unconditional gate). The new page independently calls its own authorization check — never relies on `(dashboard)/layout.tsx`'s broader gate alone, and is never nested under `/projects/**`.

**Never:** No new nav item (Decision #5). No date-range filter on Money Flow mode (Decision #2). No recomputation of `retainedMessage`/`formatSharePercent`'s existing formula — the exact same math, duplicated per this codebase's established per-module convention, never centralized into a new shared utility as part of this story. No node-position dragging/persisted custom layout. No project-wide unscoped view ever shown to a `partner`/`sub_partner` actor, under any view mode (Decision #3's privacy boundary, absolute).

## Implementation Notes

**Library:** `@xyflow/react@12.12.0` (confirmed current, `dist-tags.latest` on npm as of 2026-09-26; peer range `react/react-dom >= 17`, compatible with this repo's React 19). `pnpm audit` is clean with it pinned — no override needed (unlike `exceljs`/`uuid` in Story 5.8).

**Authorization (`authorize.ts`):** exactly per the Code Map. `ownership_structure:view_project` is a plain `new Set(["owner_admin"])` role-table entry, checked via `authorizeScope()`, no self-access override — mirrors `investment_transactions:list`. `ownership_structure:view_partner` is the SAME action for both a Partner's own slice (`?partnerId=`) and a Sub-partner's own even-narrower slice (`?subPartnerId=`) — added to `SELF_ACCESS_ACTIONS`, checked via `authorize()` with `resourceRef.ownerId` resolved by the route from whichever share the query param names (mirrors `investment_transactions:view_audit`/`withdrawal_status:view`'s exact "resolve target share first, then authorize" shape). 14 new tests in `authorize.test.ts` cover both actions per role (5 for `ownership_structure:view_project`, 9 for `ownership_structure:view_partner`, including a `project_admin`-denial case added to both for parity), case-insensitive matching, the co-partner/sibling-Sub-partner denial cases, and the nonexistent-actor edge case.

**`ownership-structure.ts` — one deliberate, documented deviation from the Code Map's literal wording:** the Code Map describes `assembleOwnershipStructure` as building "the node tree per Decision #2's three-mode field set (`sharePercent`/`retainedPercent`, ...)". It does NOT compute `retainedPercent`. Decision #2's retained-% formula (`sharePercent - sum(current Sub-partner sharePercent)`, going negative when over-allocated, no clamping) is `shares/page.tsx`'s own `retainedMessage`/`formatDifference` — plain `Number()` arithmetic on already-formatted display strings. `packages/core`'s `noRawMoneyArithmetic`/`security` lint rules forbid that kind of raw arithmetic outside `decimal-math.ts`, and every existing duplicate of this exact formula (per this codebase's own established per-module convention, referenced directly in the task brief) lives in `apps/web` — never in `packages/core`. So `assembleOwnershipStructure` returns each node's own raw `sharePercent` (both a Partner's and each of their Sub-partners'), and `structure-layout.ts`'s `computeRetainedPercent` (a byte-for-byte port of `retainedMessage`'s math, `apps/web`-side) derives the retained % for display, from data the tree already carries. Every other part of the Code Map's shape is followed as written: `Map`-bucket-then-`sumMoney()`-reduce for Money Flow (mirrors `reports.ts`'s `assemblePaymentModeReport()`), Actual Amount reuses the `investment-adjustment.ts` *technique* (not its stored `actualPaid`), only `status: "active"` rows count, current-shares-only.

**Authorization/page-shape deviation (task's own explicit ask to document):** the Code Map's `structure/[projectId]/page.tsx` entry describes the page itself calling `authorize()`. I deliberately did not do that. A dedicated investigation (forked sub-agent, full transcript available on request) confirmed there is no precedent anywhere in this codebase for a page component calling `authorize()`/`authorizeScope()` directly with a `ResourceRef`/`scopeOwnerIds` it resolved itself — every self-access-capable, *interactive* screen (Money History, Reports — the closest prior art to this story, both `"use client"` against a REST route) does so through a dedicated `app/api/**/route.ts` handler instead; the two true server-component pages that DO call a guard directly (`home/page.tsx`, `audit-history/page.tsx`) are non-interactive and reject via `redirect("/")`, which is wrong here (Decision #7's view-mode toggle and Decision #6's client-side drill-down both need local component state that a full-page redirect-based guard can't support without re-fetching on every interaction). I introduced `GET /api/projects/[id]/ownership-structure` (`apps/web/app/api/projects/[id]/ownership-structure/route.ts`), mirroring `GET /api/projects/[id]/my-withdrawal-status`'s exact AD-1 ordering (session → project existence → query parsed → [project scope: `authorizeScope()`] or [partner/sub_partner scope: resolve target share → `authorize()`] → remaining data fetch → assemble → 200/403/404). This is where the frozen I/O matrix's literal "403" outcomes live and are tested (19 tests, `route.test.ts`, run against every scope/role combination named in the task's "specific correctness properties" list, including the mixed-scenario "Partner A vs. Partner B with a large distinct amount" regression convention). `structure/[projectId]/page.tsx` itself satisfies "own guard, independent of the shell" structurally: it renders nothing but a loading skeleton until this one authorize()-gated fetch resolves, and any non-2xx response (401/403/404) renders only the generic error state — never partial or leaked data — regardless of which of the 3 roles `(dashboard)/layout.tsx`'s shell already admitted.

**Client-side drill-down/view-mode mechanics:** the page fetches the tree exactly ONCE per initial scope (the `useEffect` dependency array is `[projectId, initialPartnerId, initialSubPartnerId]` only). View-mode toggling is a plain `useState` read by `StructureCanvas`. Drill-down (Owner/Admin clicking a Partner node in the full tree) is also plain client state (`drillPartnerId`) that filters the ALREADY-FETCHED full tree's `partners` array down to the clicked one — no second fetch, no second `authorize()` call, since the Owner/Admin already legitimately has the whole tree in hand. A judgment call, documented here: drilling down does NOT update the browser URL (no `router.push`/`history.replaceState`) — only the initial scope (set by the entry-point link) is reflected in the address bar. This keeps the mechanism simple and avoids the risk of a URL-driven re-fetch fighting Decision #6/#7's "no re-fetch" requirement; the "Back to full Project" button is the only way back, which the frozen AC/matrix only requires to exist, not to be a specific URL.

**Visual design (no spec existed for this screen):** custom `@xyflow/react` node components (`StructureCanvas.tsx`) reuse `packages/ui`'s `Amount`/Card token classes (`nb-card`, `rounded-el`, `border-border`, `bg-surface`) rather than the library's default node look; connector `Handle`s are visually hidden (near-zero size/opacity) since there's no user-facing "connect nodes" affordance. Layout is a simple deterministic left-to-right tree (`structure-layout.ts`'s `buildNodesAndEdges`): one column per Partner sized to fit that Partner's own Sub-partner count, Project root centered above. No new `packages/ui` component was added — the diagram's custom nodes are page-local (`apps/web`), mirroring `home/page.tsx`'s own `PartnerOverviewCard`/`sharePercentBadge` precedent of composing existing `packages/ui` primitives inline rather than adding a new shared component for a single-screen visual pattern; this also sidesteps the Tailwind v4 `packages/ui` content-detection gotcha entirely, since every class used lives in `apps/web`'s own already-scanned files. Screenshots from the live verification (below) are available on request but weren't committed to the repo.

## Spec Change Log

**2026-09-26, post-review, Decision #2's "Total Out" wording corrected (Money Flow mode never sums a `moved_to_project` leg on top of its parent withdrawal):**

**What was wrong:** Decision #2 (frozen Intent, above) literally says Total Out is "the sum of active `money_withdrawn` + `moved_to_project`-as-source amounts." Read literally, that asks for BOTH the withdrawal transaction's own `amount` AND, separately, the amount of any `moved_to_project` destination-allocation leg it was later split into — but a `moved_to_project` leg is not a second, additional flow of money out of the share; it's a description of WHERE PART OF the already-recorded withdrawal amount ended up. `withdrawal_destination_allocations`/`money_movements` exist precisely to answer "where did this already-withdrawn money go next," not "how much MORE money left this share." Summing both would double-count that leg's own amount. This was an imprecise frozen wording on my (the spec author's) part, not a bug in the implementation.

**What replaced it:** Total Out is the sum of every `status: "active"` `withdrawal_transactions.amount` row for the share, all-time, no date filter — full stop. A withdrawal later moved to another Project via a destination allocation is still counted exactly once, at the moment the withdrawal itself was recorded; the destination-allocation/money-movement record is never separately added. `packages/core/src/ownership-structure.ts`'s own doc comment on `totalOut` (both the Partner and Sub-partner node interfaces) states this explicitly. A new regression test (`ownership-structure.test.ts`) constructs a real withdrawal with a `moved_to_project` destination-allocation leg and asserts Total Out equals the withdrawal's own amount exactly once, not the amount plus the leg.

**2026-09-26, post-review, I/O matrix's "unauthenticated → 403" row reconciled to the actual, correct, established convention (401):**

**What was wrong:** The frozen I/O & Edge-Case Matrix's row for "A different Partner/Sub-partner, or an unauthenticated session, requests a Partner-scoped view they don't own" states the expected error code as a single "403" covering both cases. For the unauthenticated case specifically, this doesn't match this codebase's own long-established, correct convention (every other route in this app returns 401 for no session, reserving 403 for "authenticated but not permitted") — an inconsistency introduced when I wrote a general-purpose matrix row instead of separating the two distinct actor states.

**What replaced it:** The route (`GET /api/projects/[id]/ownership-structure`) returns 401 for an unauthenticated request and 403 for an authenticated request lacking permission, exactly like every other route in this codebase. `route.test.ts`'s test for this case is named accordingly ("returns 401 (not 403) for an unauthenticated request to a Partner-scoped URL"). No behavior changed — the code was already correct; only the frozen matrix's own wording and the test's original name needed reconciling with it.
