## Intent

**Problem:** FR-38/FR-39 ask for 10 standard reports (Project Money, Partner, Sub-partner, Money Added, Withdrawal, Available Balance, Money Movement, Payment Mode, Adjustment, Money History), each returning only data the requesting actor is permitted to see, filterable by date/project/person. Unlike Stories 5.4-5.6 (one bespoke dashboard view per role, no new `authorize.ts` action, no REST API), Reports is architecturally different: `ARCHITECTURE-SPINE.md` maps it to a dedicated `apps/web/app/api/reports/**` route namespace, and the AC's own text says `authorizeScope()` is "extended to report generation" — a real API surface needing real authorization, not a page-level gate. The `ReportTile` component (`packages/ui`) already exists, built but unused, confirming a tile-grid entry point was always the intended shape. Report Export (Excel/PDF) is explicitly Story 5.8's job, not this one — this story only produces the on-screen, filterable, permission-scoped report data.

**Approach:** Confirmed with the user 2026-09-25:
1. **All 10 report types ship in this story**, not a subset — 6 of the 10 reuse already-built infrastructure directly (see Decision #3), keeping the genuinely new surface area to 4 report types' worth of aggregation, not 10.
2. **One new `authorize.ts` action per report type** (`reports:project_money`, `reports:partner`, `reports:sub_partner`, `reports:money_added`, `reports:withdrawal`, `reports:available_balance`, `reports:money_movement`, `reports:payment_mode`, `reports:adjustment`, `reports:money_history`) — 9 of the 10 grant `owner_admin`/`partner`/`sub_partner` (mirrors `money_history:list`'s existing grant); `reports:money_movement` alone grants `owner_admin` only, mirroring `money_movements:list`'s own already-established, more restrictive grant (a deliberate, documented carry-over, not a new restriction invented for this story). This uniform two-tier grant (9-vs-1, not 10 bespoke role lists) is easy to verify and avoids the risk of subtly mis-mirroring 10 different existing permission sets from memory.
3. **6 of the 10 report types are thin filters over the EXISTING `assembleMoneyHistory()`/`resolveMoneyHistoryScope()` (Story 5.1) — zero new money-computation logic.** `MoneyHistoryEntry.type` already distinguishes `"money_added"` | `"money_withdrawn"` | `"moved_to_project"` | `"given_to_person"` | `"added_to_available_balance"` | `"used_from_available_balance"` | `"adjustment"`, and every entry already carries `paymentMode`. Mapping:
   - **Money History** = every entry, unfiltered by type (the full existing feed, exposed via the Reports tile grid).
   - **Money Added** = entries where `type === "money_added"`.
   - **Withdrawal** = entries where `type === "money_withdrawn"`.
   - **Money Movement** = entries where `type === "moved_to_project"` (owner_admin-only per Decision #2 — the underlying money-movements domain concept, Story 4.8).
   - **Adjustment** = entries where `type === "adjustment"`.
   - **Payment Mode** = a NEW small second-order pure function, `assemblePaymentModeReport()`, grouping the SAME already-assembled entries (restricted to `type` values that carry a real `paymentMode`: `"money_added"`/`"money_withdrawn"`) by `paymentMode`, summing `amount` per mode via `sumMoney` — operates on `assembleMoneyHistory()`'s OUTPUT, not raw port data; does not modify `assembleMoneyHistory()` itself (Open/Closed).
   All 6 reuse `MoneyHistoryFilters` (`dateFrom`/`dateTo`/`projectId`/`personName`) and `resolveMoneyHistoryScope()` completely unchanged — the type-filter is applied AFTER `assembleMoneyHistory()` returns its already-scoped, already-filtered array, never by duplicating its logic.
4. **4 report types are genuinely new aggregations** (packages/core, `reports.ts`, new sibling module — mirrors `partner-dashboard.ts`/`sub-partner-dashboard.ts`'s own "new sibling per concern" Open/Closed convention): **Project Money** (one row per Project the actor can see, mirrors the dashboards' own per-actor sums but broken out per-Project instead of summed system-wide), **Partner** (one row per current Partner Share visible to the actor), **Sub-partner** (one row per current Sub-partner Share visible to the actor), **Available Balance** (one row per current `AvailableBalance` visible to the actor, reusing `AvailableBalancePort.listAll()` directly, mirrors the dashboards' own `totalAvailableBalance` sum broken into per-share rows). All 4 reuse the exact self-access filtering technique `assemblePartnerDashboard()`/`assembleSubPartnerDashboard()` already established: `owner_admin` sees every row system-wide; `partner`/`sub_partner` see only rows attributable to their own current Share(s) (`userId` case-insensitive match → set of own `shareId`s → filter). This is not a new scoping invention, it's the fourth application of an already-proven pattern.
5. **A `sub_partner` actor's own rows in "Partner" report are naturally empty** (their `userId` never appears on any `currentPartnerShares` row, so their own-share-id set is naturally empty) — this falls out of Decision #4's filtering technique automatically, with no special-casing needed, and is consistent with Story 5.6's frozen "no visibility into other Partners or Sub-partners" rule. Symmetrically, a `partner` actor's own rows in "Sub-partner" report are their own linked Sub-partners only (mirrors Story 5.5's `mySubPartners`, now carrying each Sub-partner's own money too, via the same shareId-set filtering — a genuinely new capability, but one that only ever shows a Partner their OWN Sub-partners' data, never another Partner's).
6. **One shared, parameterized presentation**, not 10 bespoke pages: `apps/web/app/(dashboard)/reports/page.tsx` (the tile grid, reusing the existing unused `ReportTile` from `packages/ui`, one tile per report type the actor's role is granted, EXPERIENCE.md's "never shown disabled/blocked" nav rule extended to tiles — a role not granted a given `reports:*` action never sees that tile) → `apps/web/app/(dashboard)/reports/[type]/page.tsx` (the report viewer: filter controls + a table of rows, `"use client"`, fetching `GET /api/reports/[type]`) — mirrors this codebase's established "use client page + REST API" shape (e.g. `add-money`/`withdraw-money`/`shares` pages), NOT the Epic-5-dashboard server-component shape, since Reports genuinely needs live filter interaction the dashboard pattern doesn't support.
7. **One shared dynamic route**, `GET /api/reports/[type]`, not 10 separate route files — an internal per-type dispatch table (type slug → `{ action, handler }`) inside the one route, avoiding 10 near-duplicate files for the shared "resolve actor, parse filters, call `authorizeScope()`" boilerplate. URL slugs are kebab-case (`project-money`, `partner`, `sub-partner`, `money-added`, `withdrawal`, `available-balance`, `money-movement`, `payment-mode`, `adjustment`, `money-history`), distinct from the colon-namespaced `authorize.ts` action strings.
8. **Filter semantics differ by report shape, not applied uniformly**: the 6 `MoneyHistoryEntry`-based types (Decision #3) support `dateFrom`/`dateTo`/`projectId`/`personName`, reusing `MoneyHistoryFilters` as-is. The 4 new aggregate types (Decision #4) represent current-state rollups, not a dated event stream — they support `projectId`/`personName`-equivalent narrowing only, no date filter (a documented scope decision, not an oversight: a Partner Share doesn't have a meaningful "date" to filter by, only its underlying transactions do, and those are already covered by the other 6 report types).
9. **The Reports nav item opens to all three roles in this story** (`owner_admin`/`partner`/`sub_partner`), matching `EXPERIENCE.md`'s explicit "Everyone (scoped)" IA table entry and the AC's own "any authorized user" framing — unlike Stories 5.4-5.6's one-role-at-a-time dashboard widening, Reports is one shared feature scoped by permission per report type, not a bespoke view per role. No new session guard is needed — the outer `(dashboard)` shell already admits all three roles as of Story 5.6; this story only widens the `reports` `NAV_ITEMS` entry's own `roles` field and adds its `href`.
10. **`packages/ui`'s `ReportTile` is reused completely unchanged** (Open/Closed) — it's a pure presentational component (icon badge + name + description) with no `href`/`onClick` prop of its own; the page wraps each tile in a `<Link>` to `/reports/[type]`.

## Boundaries & Constraints

**Always:** Every sum uses `sumMoney`/`subtractMoney`/`compareMoney` (AD-2). Only CURRENT Partner/Sub-partner Shares are considered for the Partner/Sub-partner/Project Money report types (mirrors every existing current-shares convention). `assembleMoneyHistory()`, `resolveMoneyHistoryScope()`, `assemblePartnerDashboard()`, `assembleSubPartnerDashboard()`, `assembleOwnerAdminDashboard()` are all reused, never forked or reimplemented. Every `apps/web/app/api/reports/**` request calls `authorizeScope()` with the report-type-specific action BEFORE touching data (AD-1) — this route handler is a real API route, unlike the Epic 5 dashboard pages, so AD-1 applies here in full, including the ordering rule (`authorizeScope()` before any DB read — a documented, previously-unfixed drift exists elsewhere in this codebase for this exact ordering, `deferred-work.md`'s `destination-allocations` entry; do not repeat it here).

**Never:** No change to `assembleMoneyHistory()`'s, `resolveMoneyHistoryScope()`'s, `assemblePartnerDashboard()`'s, or `assembleSubPartnerDashboard()`'s own behavior or signatures. No Report Export (Excel/PDF) — Story 5.8's job entirely; this story's report viewer only ever renders an on-screen table. No new session guard — the shell is already open to all three roles as of Story 5.6. No 10 separate route files — one shared dynamic route (Decision #7). No date filter on the 4 aggregate report types (Decision #8). No tile shown for a report type the actor's role isn't granted (EXPERIENCE.md's rule, extended from nav items to report tiles).

## Implementation Notes

**Followed the Code Map's overall shape (one shared dynamic route, one new `reports.ts` module, 10 new `authorize.ts` actions, a widened nav item) with a few deliberate deviations, all documented below.**

**Deviation #1 — `reports.ts`'s 4 aggregate functions all take `actorRole` explicitly, not just `actorUserId`.** The Code Map's own signatures list `assemblePartnerReport(actorUserId, raw)`/`assembleSubPartnerReport(actorUserId, raw)`/`assembleAvailableBalanceReport(actorUserId, raw)` without `actorRole` (only `assembleProjectMoneyReport` lists it). But `owner_admin`'s "every row system-wide" behavior is a genuinely different branch from "my own current Share(s) only" — only the role, not the userId alone, can distinguish them (an owner_admin's own `userId` is never itself a Partner/Sub-partner Share's `userId`, so without the role check an owner_admin would incorrectly see `[]` instead of everything). Added `actorRole` uniformly to all 4 for the identical reason `assembleProjectMoneyReport` already needed it, so all 4 aggregate functions read identically rather than 3 following one convention and 1 following another.

**Deviation #2 — the route's per-type dispatch is a lookup table for slug→`Action` (for the 404/authorize step) plus two dispatch *functions* (`loadMoneyHistoryBasedReport`/`loadAggregateReport`) rather than a single table of `{ action, handler }` closures.** The 10 branches' data-fetching needs differ enough (different port combinations, different raw-data shapes) that a uniform `handler` closure signature would have needed a lossy common denominator or an `any`-typed escape hatch; two explicit, type-safe dispatch functions with an internal `switch`/`if`-chain stayed just as centralized (still one file, no 10 near-duplicate routes) while keeping every branch's exact types checked by `tsc`.

**Payment Mode, Project Money, Partner, Sub-partner, and Available Balance report row shapes were all implementer judgment calls (Code Map left exact column layout open) — final shapes:**
- `PaymentModeReportRow`: `{ paymentMode, totalAmount, entryCount }` — one row per mode with ≥1 matching entry (a mode with zero entries never appears).
- `ProjectMoneyReportRow`: `{ projectId, projectName, totalAdded, totalWithdrawn, totalAvailableBalance }`.
- `PartnerReportRow`: `{ partnerId, name, projectId, projectName, sharePercent, totalAdded, totalWithdrawn, totalAvailableBalance }` — deliberately NOT rolled up with a Partner's own Sub-partners' money (mirrors `assemblePartnerDashboard()`'s own "My Sub-partners is structural only, never a financial rollup" precedent one level over — a Sub-partner's money belongs to the Sub-partner report, not folded into their parent Partner's row here).
- `SubPartnerReportRow`: `{ subPartnerId, name, partnerId, projectId, projectName, sharePercent, totalAdded, totalWithdrawn, totalAvailableBalance }` — carries the parent `partnerId` so a viewer can see which Partner a row rolls up under.
- `AvailableBalanceReportRow`: `{ partyType, shareId, name, projectId, projectName, balance }` — one row per real `available_balances` row (Decision #4: reuses `AvailableBalancePort.listAll()` directly, never re-derived from transactions).

**Icon color choices (`apps/web/lib/report-catalog.tsx`, judgment call, Code Map left this open):** `"adjustment"` is amber (`#E8A317`) per DESIGN.md's own frozen, explicitly-named choice. This palette (`packages/ui/src/styles/tokens.css`) has only 6 non-neutral hues (`accent`/`success`/`danger`/`info`/`violet`/`amber`) plus one neutral slate (`#475569`) — 7 total swatches for 10 tiles, so a few reuses were unavoidable, chosen to match an existing nav-badge/semantic-meaning tie wherever one exists rather than picked arbitrarily:
- Money Added → `success` (matches the Add Money nav badge — "money added" is already that color's established meaning).
- Withdrawal → `danger` (matches the Withdraw Money nav badge).
- Available Balance → `violet` (matches the Available Balance nav badge).
- Money History → neutral slate (matches its own existing nav-badge color exactly, unchanged from before this story).
- Project Money and Money Movement both → `accent` (no existing single-color precedent for either; `accent` is the Projects nav badge's own color, and Project Money is fundamentally about Projects — Money Movement reuses it too since it moves money *between* Projects and is `owner_admin`-only, so the two tiles only ever co-render for that one role).
- Partner → `info`/teal (matches the Partner Shares nav badge).
- Sub-partner and Payment Mode both → neutral slate (no thematic nav-badge precedent for either; reused rather than forcing a 7th distinct hue that doesn't exist in the palette).
- Icons: `Building2` (Project Money), `Users` (Partner), `UserRound` (Sub-partner), `Plus`/`Minus` (Money Added/Withdrawal, matching Add/Withdraw Money's own nav icons), `Wallet` (Available Balance, matching its own nav icon), `ArrowLeftRight` (Money Movement), `CreditCard` (Payment Mode), `RotateCcw` (Adjustment, matching Adjust Next Time's own nav icon), `History` (Money History, matching its own nav icon) — all `lucide-react`, all already used elsewhere in this codebase for the same concepts where a precedent existed.

**Tile-visibility role list (`report-catalog.tsx`'s `REPORT_DEFINITIONS.roles`) is a separately-maintained local copy of `authorize.ts`'s `reports:*` grants, not a live `authorizeScope()` call per tile** — mirrors `(dashboard)/layout.tsx`'s own `NAV_ITEMS.roles` field's identical, already-established convention (that file's `moneyHistory`/`adjustNextTime` items hardcode their role list too, rather than querying `authorize.ts` at render time). The real, enforced gate is always `GET /api/reports/[type]`'s own `authorizeScope()` call; this list only controls which tile is *offered*.

**`reports/[type]/page.tsx`'s filter semantics**: the 5 `MoneyHistoryEntry`-shaped types (`money-history`, `money-added`, `withdrawal`, `money-movement`, `adjustment`) plus `payment-mode` (6 total, matching Decision #3's "6 report types reuse `assembleMoneyHistory()`") all show the date-range filter; the 4 aggregate types (`project-money`, `partner`, `sub-partner`, `available-balance`) don't (Decision #8). `personName` narrowing on the 4 aggregate types is applied only against rows that actually carry a `name` field (Partner/Sub-partner/Available Balance) — a documented no-op for Project Money, which has no person concept; this wasn't spelled out as its own I/O matrix row, so it's an implementer judgment call, not a frozen requirement.

## Review Triage Log

3-layer review (blind-hunter, edge-case-hunter, verification-gap). No live security/data-leak bugs -- all three reviewers independently confirmed cross-party isolation is genuinely correct in the underlying code (the 10 `authorize.ts` grants are exactly right, AD-1 ordering holds across all 10 dispatch branches, the self-access filtering in `reports.ts` genuinely restricts non-owner_admin actors). One real (Low) robustness bug and seven test-coverage gaps, all applied:

1. **[Applied, Low, real bug]** `apps/web/app/api/reports/[type]/route.ts`'s `ACTION_BY_SLUG`/`ENTRY_TYPE_BY_SLUG` were plain `{}` object literals -- a request to `GET /api/reports/constructor` (or `toString`/`valueOf`/`hasOwnProperty`) resolved to `Object.prototype`'s own inherited member via the prototype chain (a truthy value), bypassing the `if (!action)` 404 guard and crashing with an unhandled 500 inside `authorizeScope()` instead.
