## Intent

**Problem:** FR-37 asks for a Sub-partner's own scoped dashboard: "the same category of cards as a Partner dashboard [FR-36], scoped strictly to that Sub-partner's own data — no visibility into other Partners or Sub-partners" (epics.md Story 5.6). Story 5.5 deliberately stopped short of `sub_partner` — `requireOwnerAdminOrPartnerSession()`'s own doc comment names this story by number as the one that widens the shell further. Every piece this story needs already exists one level down: `money_history:list`/`adjust_next_time:view` already grant `sub_partner` at the `authorize.ts` role-table level (Story 5.1/5.3); `resolveMoneyHistoryScope()` is already role-agnostic and explicitly handles a `sub_partner` actor's own Sub-partner Shares; `assemblePartnerDashboard()` (Story 5.5) already proved the exact "filter current Shares by `userId`, aggregate money across every one of the actor's own `shareId`s" pattern this story needs one role over.

**Approach:**
1. **The shell opens to `sub_partner` now**, via a new `requireOwnerAdminOrPartnerOrSubPartnerSession()` (mirrors `requireOwnerAdminOrPartnerSession()`'s exact shape, one role wider). `requireOwnerAdminSession()` and `requireOwnerAdminOrPartnerSession()` stay completely untouched (Open/Closed) — this is a new sibling, not a widened version of either.
2. **Nav items widen the same 3 items Story 5.5 already opened to `partner`** (Home, Money History, Adjust Next Time) to also admit `sub_partner` — every other item (Projects, Partner Shares, Add Money, Withdraw Money, Available Balance's own page, Reports, Users, Permissions, Audit History) stays hidden, unchanged from today.
3. **"My Sub-partners" has no equivalent here and is dropped, not shown empty.** A Sub-partner has no sub-partners of their own (the data model has no such concept — `subpartner_shares` has no `parentSubPartnerId`), so this isn't a data gap to work around, it's a category that doesn't exist for this role. This dashboard shows: My Projects (per-Project Share %), Money Added, Money Withdrawn, Available Balance, Pending, Extra Paid, Withdrawal Keep for Later, and Money History (reachable via nav) — 8 of Story 5.5's 9 data points, "same category of cards" read as "the applicable subset," matching this story's own AC text.
4. **No visibility into the parent Partner is shown**, even where the Story 2.6 `subPartnerVisibilityGrant` is on. That grant governs a Sub-partner's ability to view their *parent Partner's own Partner Share/context* (`partner_shares:view_grant`) — a separate, existing, already-built feature (Story 2.6) with its own access path. This story's own AC is explicit: "no visibility into other Partners or Sub-partners." Surfacing the parent Partner's data here, even conditionally, would contradict that literal text. If the human wants the 2.6 grant surfaced on this dashboard too, that's a future story's explicit decision, not an inferred default here.
5. **This dashboard is a server component calling ports directly**, exactly mirroring Story 5.5's Partner Dashboard precedent one role over — no new `authorize.ts` action needed; the page-level role gate is what protects the data.
6. **"My Projects, My Share %" is a per-Project breakdown list, money totals are aggregates across all of the actor's own Projects** — identical structure to Story 5.5's Partner Dashboard, substituting `subPartnerId` for `partnerId` throughout. A Sub-partner's `userId` can be linked to more than one current `SubPartnerShare` row (unindexed, no uniqueness constraint, `schema.ts`) — exactly as a Partner's `userId` can be linked to more than one current `PartnerShare` row — so this must aggregate across every one of the actor's own `subPartnerId`s, never assume exactly one.
7. **A new, separate pure function** (`assembleSubPartnerDashboard()`, `packages/core`) is added rather than extending `assemblePartnerDashboard()` with a role parameter — mirrors this codebase's established Open/Closed convention (new sibling guard/module per role-widening, not a branch inside an existing one), and the two functions' raw-data needs genuinely differ: this one has no reason to fetch `currentPartnerShares` at all.

## Boundaries & Constraints

**Always:** Every sum uses `sumMoney`/`subtractMoney`/`compareMoney` (AD-2). Only `status: "active"` investment/withdrawal transactions count (mirrors every existing active-only sum). Only CURRENT Sub-partner Shares are considered (via the existing `listAllCurrentSubPartnerShares()`, unchanged). Pending and Extra Paid (and Keep for Later / Extra Taken) are always summed separately by `adjustmentType`, never netted against each other (AD-4, unchanged). Money stays attributed to the exact `shareId` it belongs to (AD-4) — this dashboard's totals only ever include rows where `partyType === "sub_partner"` and `shareId` is one of the actor's own current `subPartnerId`s.

**Never:** No new `authorize.ts` action. No change to `assembleMoneyHistory()`, `assembleOwnerAdminDashboard()`, `assemblePartnerDashboard()`, `resolveMoneyHistoryScope()`, `requireOwnerAdminSession()`, or `requireOwnerAdminOrPartnerSession()` — all reused/left byte-for-byte unchanged. No "My Sub-partners"-shaped section (Decisions #3). No surfacing of the parent Partner's own data via the Story 2.6 grant or any other path (Decisions #4). No nav item shown for a role whose underlying page would 403 on click (EXPERIENCE.md's rule, unchanged). No embedding of Money History's own list/filter UI on this page.

## Code Map

- `apps/web/lib/session-guard.ts` — add `requireOwnerAdminOrPartnerOrSubPartnerSession(): Promise<Session>`, mirroring `requireOwnerAdminOrPartnerSession()`'s exact shape (`requireSession()` + a role check), admitting `owner_admin`, `partner`, OR `sub_partner`. `requireOwnerAdminSession()`/`requireOwnerAdminOrPartnerSession()` stay untouched.
- `apps/web/app/(dashboard)/layout.tsx` — swap the new guard in. Widen `home`/`moneyHistory`/`adjustNextTime`'s `roles` to include `sub_partner` (every other `NAV_ITEMS` entry stays `["owner_admin"]`, unchanged). Widen the role-filter cast (`actor.role as "owner_admin" | "partner" | "sub_partner"`) and `SidebarNavItem.roles`'s type (`SidebarNav.tsx`) to include `"sub_partner"`.
- `packages/core/src/sub-partner-dashboard.ts` (new) — pure `assembleSubPartnerDashboard(actorUserId, raw: { investmentTransactions, withdrawalTransactions, availableBalances, investmentAdjustments, withdrawalAdjustments, currentSubPartnerShares, projectNamesById }): SubPartnerDashboardSummary`. Filters `currentSubPartnerShares` to `userId === actorUserId` (case-insensitive, mirrors `assemblePartnerDashboard()`'s identical check) → `myProjects: { projectId, projectName, subPartnerId, sharePercent }[]`. For the resulting set of `subPartnerId`s: sums active investment/withdrawal/balance rows (filtered to `partyType === "sub_partner"` and `shareId` in that set) into `totalMoneyAdded`/`totalMoneyWithdrawn`/`totalAvailableBalance`. Sums `investmentAdjustments`/`withdrawalAdjustments` (same filter) separately by `adjustmentType` into `totalPending`/`totalExtraPaid`/`totalKeepForLater`/`totalExtraTaken`. No `currentPartnerShares` input needed — this function has no reason to touch the Partner Shares table at all.
- `packages/core/src/index.ts` — barrel-export the new module.
- `apps/web/app/(dashboard)/home/page.tsx` (existing, extend) — add a third role branch: `sub_partner` → new rendering using `assembleSubPartnerDashboard()` (constructs `investmentTransactionPort`/`withdrawalTransactionPort`/`availableBalancePort`/`investmentAdjustmentPort`/`withdrawalAdjustmentPort`/`subPartnerSharePort`/`projectPort` — a strict subset of `PartnerDashboard`'s own port list, no `partnerSharePort`) — a `StatCard` row for the 6 aggregate totals (identical labels/layout to `PartnerDashboard`'s own, minus nothing — same 6), a `myProjects` list (reuse `ShareRow`/`ShareList`, mirroring `PartnerDashboard`'s own precedent), no "My Sub-partners" section. `owner_admin`/`partner` branches stay byte-for-byte unchanged.

## Implementation Notes

**Followed the Code Map essentially as written -- no structural deviations.** `requireOwnerAdminOrPartnerOrSubPartnerSession()` (`apps/web/lib/session-guard.ts`) mirrors `requireOwnerAdminOrPartnerSession()`'s exact shape one role wider; `assembleSubPartnerDashboard()` (`packages/core/src/sub-partner-dashboard.ts`) mirrors `assemblePartnerDashboard()`'s exact "filter current Shares by `userId`, build a Set of own share ids, filter every row by `partyType`+`shareId` membership" pattern, with no `currentPartnerShares` input at all (this story's own frozen Decisions #7) and no `mySubPartners`-shaped output field (Decisions #3). `SubPartnerDashboard` (`apps/web/app/(dashboard)/home/page.tsx`) mirrors `PartnerDashboard`'s exact server-component shape one role over, constructing the same investment/withdrawal/balance/adjustment ports (still needed for the 6 money totals) but specifically omitting `createPartnerSharePort()`, and omitting the "My Sub-partners" `Card` section entirely, which structurally doesn't render (not an `EmptyState` -- Decisions #3's "a category that doesn't exist for this role", not "a data gap").

**`SubPartnerDashboardProjectRow` widens the Code Map's stated shape the same documented way `PartnerDashboardSubPartnerRow` did in Story 5.5** -- `subPartnerId` is included for a stable React list key, mirroring that story's own precedent (itself mirroring `OwnerAdminDashboardRawData`'s Story 5.4 precedent) of a harmless, documented Code Map widening for exactly this reason.

**Renders 6 stat cards (not the Code Map's literal "6 aggregate totals" text expanded further) -- `totalExtraTaken` is computed by `assembleSubPartnerDashboard()` but deliberately not rendered**, for the identical reason `PartnerDashboard` doesn't render it: it's AD-4 completeness (mirroring `totalKeepForLater`'s own three-way `adjustmentType` split), not one of this story's frozen AC/I-O-matrix's 8 named data points. Same judgment call as Story 5.5's own Implementation Notes, made identically here for consistency between the two sibling dashboards.

**`sharePercentBadge()` and `formatSharePercent()` (both pre-existing, `home/page.tsx`) are reused unmodified by `SubPartnerDashboard`** -- no Sub-partner-specific copy was created; both are share-percent-formatting concerns generic to either role's "My Projects" row, exactly as their existing doc comments already describe (both already say "My Projects" / "My Sub-partners" generically, not Partner-specifically).

**`apps/web/app/(dashboard)/projects/layout.tsx` needed NO changes and required no new test** -- verified live (see below) that it already correctly rejects a `sub_partner` session for the entire `/projects/**` subtree, since it calls the byte-for-byte-unchanged `requireOwnerAdminSession()`, whose own role check (`actor.role !== "owner_admin"`) was never role-enumerated -- it already rejected every non-owner_admin role, `sub_partner` included, from the moment Story 5.5 wrote it.
