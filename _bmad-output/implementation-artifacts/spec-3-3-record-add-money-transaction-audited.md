## Intent

**Problem:** Should Pay (Story 3.2) is a live calculation with nothing recorded against it — nobody can record an actual payment ("Paid Now"), and there's no audit trail or protection against a double-submitted form creating two transactions for one real payment.

**Approach:** New `investment_transactions` table (one row per recorded payment, keyed by `(partyType, shareId)` — `shareId` is `PARTNER_SHARE.partnerId` or `SUBPARTNER_SHARE.subPartnerId` (the stable identifier, never a versioned row's own `id`, and never `USER.id` — AD-4), never a foreign key (neither source table has a uniqueness constraint on that stable id — same reason `subpartner_shares.partnerId` already isn't one). New generic `audit_log` table (entityType/entityId/action/actorUserId/oldValue/newValue/reason), reused unchanged by every later financial-write story. AD-5's full pattern: the transaction insert + its audit_log row happen in one DB transaction, and a unique `idempotencyKey` column means a double-submitted request returns the original row instead of creating a second one. Per AD-3, `sharePercent`/`shouldPay` are snapshotted onto the transaction row at creation time by re-running Story 3.2's `computeShouldPay` server-side — never trusting a client-submitted Should Pay value, and never recomputed later from a share's current state. New `investment_transactions:create` action reuses Epic 2's single-resource self-access idiom (a Partner/Sub-partner can record their own payment; Owner/Admin can record anyone's) — the only Epic 3 action so far to open self-access, because this story's AC explicitly frames it as "a user (or Owner/Admin on their behalf)," unlike 3.1/3.2's deliberately-deferred Owner/Admin-only scope.

**Decisions (resolved 2026-09-24):**
- **`investment_transactions:create` gets real self-access (Epic 3's first), `investment_transactions:list` stays Owner/Admin-only.** The AC's persona ("As a user (or Owner/Admin on their behalf)") is explicit and testable, unlike 3.1/3.2's ambiguous "any authorized viewer" framing — self-service recording is this story's actual scope, not a hypothetical future consumer. Listing every transaction for a requirement, though, is oversight functionality (matches 3.1/3.2's Owner/Admin-only list precedent); a person's own transaction history view is Epic 5's job. No UI is built for self-service recording in this story (no Partner/Sub-partner-facing page exists yet) — only the API is opened, so Epic 5's dashboard can consume it later without a gate change, exactly mirroring how `should_pay:view`'s Owner/Admin-only scope was justified by the *absence* of a consuming UI; here self-access is justified by the AC explicitly requiring it regardless of UI.
- **The target share's `userId` (for the self-access check) is resolved by fetching current Partner/Sub-partner Shares *before* calling `authorize()`, mirroring Stories 2.4/2.6's identical precedent** (`partner_shares:list`/`partner_shares:view_grant` both resolve `scopeOwnerIds` via a shares fetch before the authorize call). This is the same fetch Story 3.2's Should Pay snapshot needs anyway — no duplicate DB round-trip. Session → project existence → requirement existence → shares fetch → target-share resolution (404 if `shareId` doesn't match any current share) → `authorize()` (403) → domain validation (400) → Should Pay preconditions (409, reused from 3.2) → write (201).
- **`audit_log` is a single generic table (`entityType`/`entityId`/`action`/`actorUserId`/`oldValue`/`newValue`/`reason`), not a per-entity table.** AD-5 explicitly states this table is "reused unchanged by every later financial-write story in Epic 3 and Epic 4" (3.7 edit, 3.8 cancel, Epic 4's withdrawal stories) — a generic shape now avoids a schema migration for every one of those. `reason` is nullable and unused (`null`) for this story's create-only entries; edit/cancel stories populate it.
- **The idempotency-key mechanism is a `UNIQUE` column directly on `investment_transactions`** (not a separate generic table) — the port's `recordTransaction` checks for an existing row with the same key first (returns it unchanged if found — the idempotent-replay case), and falls back to catching a unique-constraint violation on insert (the concurrent-double-submit race) by re-reading and returning the winning row, rather than erroring. Every later financial-write table (`withdrawal_transactions`, etc.) adds its own identically-shaped `idempotencyKey` column — the same *convention*, not literally the same table.
- **The atomic "transaction insert + audit_log insert in one DB transaction" requirement (AD-5) is implemented entirely inside the `packages/db` port method** (`database.transaction(async (tx) => {...})`), invisible to `packages/core` — `packages/core` never imports Drizzle (AD-9); the port's *contract* is "this call is atomic," not its mechanism.
- **`amount` ("Paid Now") uses `toMoney()`'s existing baseline validation only — no extra `> 0` floor.** AC2 explicitly requires `"0"` to be accepted ("no minimum payment enforced") — unlike `investment_requirements.amount` (Story 3.1), which does add a `> 0` floor on top of `toMoney()`.
- **`paymentMode` is a fixed enum** (`cash`, `cheque`, `neft`, `rtgs`, `imps`, `upi`, `bank_transfer`, `other` — matching epic-3-context.md's UX list verbatim), stored as `text`, validated against that exact set; an unrecognized value is a 400 `validation_error`, mirroring `requirementDate`'s format-check pattern.
- **`referenceNumber`/`notes` are optional, nullable strings** (e.g. a cash payment often has no reference number) — no format validation beyond "a string or absent."
- **No `status`/cancel column on `investment_transactions` in this story.** Cancel/reverse (Story 3.8) adds that column via its own migration when it's actually needed — building it speculatively now would be exactly the kind of ahead-of-a-real-consumer capability this codebase has consistently avoided (the `Amount`/`Checkbox` precedent).

## Boundaries & Constraints

**Always:** `POST`/`GET .../investment-requirements/[requirementId]/transactions` require a valid session (401). `POST` resolves the target Partner/Sub-partner's current share (404 if `shareId`/`partyType` doesn't match any current share for this Project) before calling `authorize()` for `"investment_transactions:create"` with `resourceRef.ownerId` set to that share's `userId` (self-access allowed; Owner/Admin always allowed; anyone else 403). `GET` uses `authorizeScope()` for `"investment_transactions:list"` (Owner/Admin-only). Project and requirement existence (incl. cross-project mismatch) are checked before any share/transaction read, mirroring 3.1/3.2. `amount`/`transactionDate`/`paymentMode` are validated before any write; the funding requirement's Should Pay preconditions (Partner Shares total 100%, no Sub-partner over-allocation — reused from Story 3.2) are re-checked at write time and mapped to the same 409 codes. Every successful `POST` writes the transaction row and one `audit_log` row in a single DB transaction; a repeated `POST` with the same `idempotencyKey` returns the original row (200, not 201) rather than creating a second one.

**Never:** No edit/cancel endpoint for a recorded transaction (Stories 3.7/3.8). No Investment Adjustment computation (Story 3.4) — this story only records the raw transaction plus its Should Pay snapshot. No change to a Partner/Sub-partner's `sharePercent` — recording a payment, of any amount, never touches `partner_shares`/`subpartner_shares`. No `DELETE` ever targets `investment_transactions` or `audit_log`.

## Implementation Notes

`InvestmentTransactionPort.recordTransaction` returns `RecordTransactionResult { transaction, created }` instead of the Code Map's literal `Promise<InvestmentTransaction>` — necessary because the frozen Boundaries text requires a repeated `POST` with the same `idempotencyKey` to return 200 (replay), not 201 (genuine insert), and no field on `InvestmentTransaction` itself can convey that distinction. The route/domain layer thread this flag through to pick the response status.

## Spec Change Log

Patch round 1 (Review Triage Log rows 1, 2, 3, 5, 7): the client-side idempotency key is now minted once per logical submission (on dialog open) and reused across a retry, instead of a fresh key per fetch call — restores the actual double-submit protection AD-5/AC4 describe. Added `matchesRequest`/`IdempotencyKeyConflictError` so a key collision with mismatched request content is rejected (409) rather than silently returning the wrong party's data. Fixed a misleading test citation and added a narrowly-scoped `packages/db/src/ports.test.ts` for the pure `isUniqueViolation` helper. Normalized blank `referenceNumber`/`notes` to `null` server-side. Added a regression test for the idempotency-key reuse-across-retry behavior.

Patch round 2 (Review Triage Log row 9, found by the orchestrator's own live-Postgres re-verification of patch round 1): `matchesRequest`'s `amount` comparison used raw string equality, which broke on Postgres's `numeric(14,2)` round-trip (a stored `"700000"` reads back as `"700000.00"`) — a genuine identical-content retry was incorrectly rejected as a key conflict. Fixed via a new `moneyEquals` decimal-math helper (fixed-point comparison, never `Number()`/`parseFloat`), with regression tests in both `decimal-math.test.ts` and `ports.test.ts` reproducing the exact scenario.

Independently re-verified after both patch rounds: `pnpm turbo run typecheck lint test build --force` (18/18 green, 293 core + 58 db + 296 web tests), `pnpm lint:boundaries` (clean), `pnpm audit` (clean), and two full live-verification passes against real Postgres (atomic transaction+audit_log write, self-access + cross-partner 403, zero-amount accepted, invalid payment mode rejected, nonexistent share 404, genuine idempotent replay now correctly returns 200, and a real key collision correctly returns 409 `idempotency_key_conflict`).
