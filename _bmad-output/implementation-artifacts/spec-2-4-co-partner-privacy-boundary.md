## Intent

**Problem:** A Partner's internal Sub-partner structure and split percentages must stay invisible to their co-partners on the same Project — but nothing currently links a "partner"-role login to a specific `partner_shares` row at all, so `authorize()`/`authorizeScope()` has no way to know "this session IS Partner B" in order to scope anything.

**Approach:** Add a nullable `userId` link (FK to `users.id`) on `partner_shares` and `subpartner_shares` — the architecture spine's own ER diagram already models this (`USER }o--|| PARTNER_SHARE : "may be"`, `USER }o--|| SUBPARTNER_SHARE : "may be"`), it has just never been built. Add a minimal "Linked user (email)" field to the existing Add/Edit Partner and Add/Edit Sub-partner dialogs so Owner/Admin can set it. Extend `authorize()`/`authorizeScope()` with an ownership-based scope check (reusing/generalizing the existing `SELF_ACCESS_ACTIONS` self-access idiom from Story 1.5) so a linked Partner can list their own Project's Partner Shares and their own Sub-partner structure, while a different Partner on the same Project gets 403, and Owner/Admin keeps unconditional full access.

**Decisions (resolved 2026-09-23):**
- **User↔Partner linkage mechanism (checkpointed with the human):** schema + minimal UI this story. `partner_shares.user_id`/`subpartner_shares.user_id` (nullable, FK to `users.id`, `ON DELETE SET NULL`) is the link. The existing Add/Edit Partner dialog and Add/Edit Sub-partner dialog (both already built, Stories 2.2/2.3) gain one new field: "Linked user (email)" — a plain text input, not a picker/dropdown. Empty = no link. This field is **required** in every POST/PATCH body from now on (an empty string means "no link", never "leave unchanged") — matches `name`/`sharePercent`'s existing full-overwrite-per-save convention (AD-3's versioning model has no partial-update semantics anywhere else, so this doesn't introduce a new pattern).
- **Email resolution happens at the route layer, not in `packages/core`.** The domain modules (`partner-share.ts`/`subpartner-share.ts`) gain a plain `userId: string | null` field on their input — already-resolved, already-validated. `apps/web`'s route handlers (which already hold a `UserPort` for the `authorizeScope()` call) resolve `linkedUserEmail` → `userId` themselves via `userPort.findUserByEmail()`, validating existence and that the resolved user's global `role` matches (`"partner"` for `partner_shares`, `"sub_partner"` for `subpartner_shares`) before ever calling the domain function. This keeps `packages/core`'s port dependencies narrow (Interface Segregation, per AGENTS.md) — the domain layer never needs a `UserPort`.
- **`partner_shares:list` opens to a linked Partner, scoped to Projects they're actually linked to — not every Project.** FR7 ("Every API/database query independently verifies... their association to the specific Project/Partner/Sub-partner records requested") applies even though Story 2.4's own AC text only tests two co-partners already on the *same* Project; a Partner with zero share in a Project has no stated business seeing that Project's roster by guessing its id. `authorizeScope()` gains an optional `scopeOwnerIds` parameter (a list of userIds legitimately scoped-in for this specific request) and a new `SCOPE_SELF_ACCESS_ACTIONS` set, generalizing the existing single-resource `SELF_ACCESS_ACTIONS`/`ResourceRef.ownerId` idiom (Story 1.5) from one owner to a list. The route computes `scopeOwnerIds` from the Project's *current* Partner Shares' `userId`s before calling `authorizeScope()`.
- **`subpartner_shares:list` opens to the linked Partner for their own `partnerId` only**, reusing the existing single-resource `authorize()`/`ResourceRef.ownerId`/`SELF_ACCESS_ACTIONS` mechanism unchanged — just adding `"subpartner_shares:list"` to that set and calling `authorize()` (not `authorizeScope()`) with `{ ownerId: partner.userId ?? "" }` once the route has already resolved the target Partner row. A `sub_partner`-role actor's own `userId` is never a `partner_shares.userId` (different table/column), so this cannot accidentally admit a Sub-partner — Sub-partner visibility is explicitly Story 2.5's job, untouched here.
- **Top-level Partner Share data (name + Share %) is not part of the privacy boundary — only Sub-partner structure is**, per AC4's explicit "plain project-level totals... not part of the privacy boundary" and FR9's grouping of "sub-partner structure, split percentages[within it]" as the hidden set. `GET .../partner-shares` (list) returns the full, unfiltered list of every Partner on the Project once a linked (or Owner/Admin) caller passes the membership check above — no per-row redaction. Only `GET .../subpartner-shares` (a specific Partner's own internal split) is boundaried per-Partner.
- **Create/update (`POST`/`PATCH`) stay Owner/Admin-only, unchanged.** Story 2.4's AC is entirely about *read* access (`403 with no data` on a cross-partner read attempt); nothing in it asks for Partner self-service editing. FR14's "Owner/Admin (or the Partner, if permitted)" self-service creation is not resolved by this story and stays out of scope — noted in Boundaries.
- **The dashboard shell (`requireOwnerAdminSession()`) stays Owner/Admin-only, unchanged.** This story only extends the *API-level* authorization gate; it does not reopen `(dashboard)`'s route group to `partner`/`sub_partner` logins. `apps/web/lib/session-guard.ts`'s current gate remains the stopgap until a story that actually needs a Partner-facing UI (per `epics.md`'s Epic 5 "Partner dashboard", or an earlier one if the roadmap changes) builds real Partner navigation. Reopening the shell now, with no Partner-facing screens behind it, would just show a Partner a broken/empty dashboard.
- **No uniqueness constraint on the link** — nothing stops the same `userId` being linked to more than one `partner_shares`/`subpartner_shares` row (across different Projects, or even accidentally within one). Not required by any AC; enforcing it is scope creep for this story.

## Boundaries & Constraints

**Always:** Every `GET .../partner-shares` and `GET .../subpartner-shares` call still requires a valid session (401 if none). `partner_shares:list` allows Owner/Admin unconditionally, or any authenticated user whose `userId` matches a `userId` on a *current* Partner Share row for the requested Project (`scopeOwnerIds`); anyone else gets 403 with no data, uniformly, whether or not the Project exists. `subpartner_shares:list` allows Owner/Admin unconditionally, or the specific linked Partner (their own `partnerId` only, via `ResourceRef.ownerId` matching `partner.userId`); anyone else gets 403. `POST`/`PATCH` on both resources keep today's Owner/Admin-only gate, checked immediately after the session check and before body parsing (unchanged ordering, unchanged from Stories 2.2/2.3). `linkedUserEmail` is validated server-side before any write: unresolvable email → 400 `validation_error`; email resolves but the user's role doesn't match (`"partner"` for Partner Shares, `"sub_partner"` for Sub-partner Shares) → 400 `validation_error`. Every existing cross-scope ownership check from Stories 2.2/2.3 (`partnerId` belongs to `projectId`, `subPartnerId` belongs to `partnerId`) stays exactly as-is — this story adds an ownership *authorization* layer on top, it does not touch or relax the existing 404 scoping-integrity checks.

**Never:** No change to `POST`/`PATCH` authorization (Owner/Admin-only, unchanged). No change to `projects:list`/`projects:view` permissions — those stay Owner/Admin-only; a linked Partner reaching these endpoints must already know the Project id (discoverability is out of scope). No reopening of the `(dashboard)` route group to non-`owner_admin` roles. No Sub-partner-role access to anything here (Story 2.5's job). No uniqueness enforcement on the User↔Partner/Sub-partner link. No audit trail for linking/unlinking a user (pre-existing gap pattern, same as every other admin action in this codebase so far).

## I/O & Edge-Case Matrix

| Scenario | Input / State | Expected Output / Behavior | Error Handling |
|----------|--------------|---------------------------|----------------|
| Cross-partner Sub-partner read blocked | Partner B (linked), requests `GET .../partner-shares/{Partner A's id}/subpartner-shares` | 403, no data | `{code: "forbidden"}` |
| Same, via direct URL/ID manipulation | Partner B, hand-typed URL with Partner A's real `partnerId` | Identical 403 — no field of Partner A's data present | `{code: "forbidden"}` |
| Partner reads their own Sub-partner structure | Partner A (linked to `partnerId` X), requests `GET .../partner-shares/X/subpartner-shares` | 200, their own current Sub-partner Shares + total | N/A |
| Owner/Admin retains full visibility | Owner/Admin, requests any Partner's `subpartner-shares` | 200, full data, unconditional | N/A |
| Co-partner top-line visibility preserved | Partner B, requests `GET .../partner-shares` (list) on a Project they're linked to (alongside Partner A) | 200, full list incl. Partner A's name + Share % — not part of the boundary | N/A |
| Partner not linked to this Project at all | Partner C (linked elsewhere), requests `GET .../partner-shares` for a Project they have no share in | 403, no data — not 404 (uniform, doesn't confirm/deny Project existence to an unrelated actor) | `{code: "forbidden"}` |
| Sub-partner role blocked entirely | `sub_partner` role, requests any `partner-shares`/`subpartner-shares` endpoint | 403 (Story 2.5's job, untouched here) | `{code: "forbidden"}` |
| Link a Partner Share to a user via email | Owner/Admin, POST/PATCH with `linkedUserEmail: "partner@x.test"` where that user has `role: "partner"` | 201/200, `userId` set on the new version row | N/A |
| Link with unknown email | `linkedUserEmail: "nobody@x.test"` | 400, no row created/versioned | `{code: "validation_error", message}` |
| Link with wrong-role email | `linkedUserEmail` resolves to an `owner_admin` or `sub_partner` user on a Partner Share (or `partner` user on a Sub-partner Share) | 400, no row created/versioned | `{code: "validation_error", message}` |
| Unlink on edit | Edit an already-linked Partner Share with `linkedUserEmail: ""` | 200, new versioned row with `userId: null` | N/A |
| Add/edit with no link | `linkedUserEmail: ""` on a fresh add | 201/200, `userId: null` | N/A |

- `packages/core/src/partner-share-port.ts` / `subpartner-share-port.ts` — `CreatePartnerShareInput`/`CreateSubPartnerShareInput` gain `userId: string | null`.
- `packages/core/src/partner-share.ts` / `subpartner-share.ts` — `PartnerShareInput`/`SubPartnerShareInput` gain `userId: string | null` (always explicitly provided, full-overwrite, no "carry forward" branch); `addPartnerShare`/`updatePartnerShare` (and Sub-partner equivalents) pass it straight through to the port's create call. No new validation here — email resolution/role-matching happens in `apps/web`, per Decisions.
- `packages/db/src/ports.ts` — `createPartnerSharePort`/`createSubPartnerSharePort`'s `create*Share` methods persist `userId`; `toPartnerShare`/`toSubPartnerShare` mappers include it in the returned object.
- `packages/core/src/authorize.ts` — extend `SELF_ACCESS_ACTIONS` with `"subpartner_shares:list"` (reuses existing single-resource `authorize()`/`ResourceRef.ownerId` logic unchanged). Add `SCOPE_SELF_ACCESS_ACTIONS: ReadonlySet<Action> = new Set(["partner_shares:list"])` and extend `authorizeScope()`'s signature with an optional `scopeOwnerIds?: readonly string[]` fourth parameter: when the action is in `SCOPE_SELF_ACCESS_ACTIONS` and `scopeOwnerIds` (case-insensitively) includes `actorUserId`, allowed — in addition to the existing role-based `PERMISSIONS[action].has(actor.role)` check, not replacing it. Fully backward-compatible (optional param; every other existing call site is unaffected).
- `apps/web/app/api/projects/[id]/partner-shares/route.ts` — **GET**: reorder to resolve the project + its current Partner Shares *before* the authorization check (needed to compute `scopeOwnerIds`); call `authorizeScope(..., scopeOwnerIds)`; uniform 403 for anyone not Owner/Admin and not in `scopeOwnerIds`, regardless of whether the Project exists; Owner/Admin (or a linked, in-scope Partner) falls through to the existing 404-if-missing-project check. **POST**: body validation grows a required `linkedUserEmail: string`; after the (unchanged) Owner/Admin-only `authorizeScope()` gate and body parsing, resolve `linkedUserEmail` via `userPort.findUserByEmail()` (400 if empty-but-required... no: empty string is valid, meaning no link; 400 only on non-empty-but-unresolvable, or resolved-but-wrong-role) before calling `addPartnerShare`.
- `apps/web/app/api/projects/[id]/partner-shares/[partnerId]/route.ts` — **PATCH**: same `linkedUserEmail` resolution/validation as POST above, before calling `updatePartnerShare`.
- `apps/web/app/api/projects/[id]/partner-shares/[partnerId]/subpartner-shares/route.ts` — **GET**: after the existing `resolveScope()` resolves the target Partner row, switch from `authorizeScope("subpartner_shares:list", ...)` to `authorize("subpartner_shares:list", { ownerId: partner.userId ?? "" }, ...)`; 403 (not 404) if it fails. **POST**: same `linkedUserEmail` resolution as the Partner Shares POST, validated against `role: "sub_partner"` instead.
- `apps/web/app/api/projects/[id]/partner-shares/[partnerId]/subpartner-shares/[subPartnerId]/route.ts` — **PATCH**: same `linkedUserEmail` resolution/validation as the Sub-partner POST.
- `apps/web/app/api/projects/[id]/partner-shares/shared.ts` / `subpartner-shares/shared.ts` — `isValidPartnerShareBody`/`isValidSubPartnerShareBody` type guards grow the required `linkedUserEmail: string` field.
- `apps/web/lib/partner-shares.ts` / `subpartner-shares.ts` — client fetch helper input types (`PartnerShareInput`/`SubPartnerShareInput`) gain `linkedUserEmail: string`.
- `apps/web/app/(dashboard)/projects/[id]/shares/page.tsx` — **modified**: fetches `GET /api/users` once on mount (existing Owner/Admin-scoped endpoint) to build a local `userId → email` lookup for pre-populating edit dialogs; Add/Edit Partner dialog and Add/Edit Sub-partner dialog each gain one new `Field`/`Label`/`Input` for "Linked user (email)" (plain text, optional, empty = no link); `handleSubmit` includes `linkedUserEmail` in every add/edit call.
- **Existing test files needing updates** (their valid-body fixtures now need a `linkedUserEmail` value, or the required-field check will reject them): `apps/web/app/api/projects/[id]/partner-shares/route.test.ts`, `.../partner-shares/[partnerId]/route.test.ts`, `.../subpartner-shares/route.test.ts`, `.../subpartner-shares/[subPartnerId]/route.test.ts`.

**Acceptance Criteria (from epics.md Story 2.4):**
- Given Partner A and Partner B on the same Project A, when Partner B requests any endpoint that would reveal Partner A's sub-partner structure, split percentages, or private transaction detail, then the response is 403 with no data.
- Given the same setup, when Partner B attempts this via direct URL/ID manipulation instead of the UI, then the result is identical — 403, no field of Partner A's data present.
- Given Owner/Admin, when they view any partner's data, then full visibility is retained.
- Given Partner A and Partner B on the same Project A, when Partner B views Project A's partner-wise summary, then Partner B sees Partner A's plain project-level totals — explicitly not part of the privacy boundary.
