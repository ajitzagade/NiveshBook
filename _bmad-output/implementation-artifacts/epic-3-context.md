# Epic 3 Context: Add Money — Flexible Investment

<!-- Compiled from planning artifacts. Edit freely. Regenerate with compile-epic-context if planning docs change. -->

## Goal

Owner/Admin can request funding for a project; every Partner and Sub-partner sees their Should Pay computed automatically from Share % (never manual math), pays any amount — more, less, or nothing, never blocked or auto-capped — and the system tracks the gap as an Investment Adjustment (Pending or Extra Paid) that carries forward into the next funding round as a *recommended*, never forced, amount. Paying, however much, never changes anyone's Share %. This epic also introduces the audit/idempotency pattern as a first-class part of every financial write — the pattern every later financial-write story in Epic 3 and Epic 4 reuses unchanged.

## Stories

- Story 3.1: Create Investment Requirement
- Story 3.2: Auto-Calculate Should Pay
- Story 3.3: Record Add Money Transaction (Audited)
- Story 3.4: Compute Investment Adjustment
- Story 3.5: Carry Forward Recommended Amount
- Story 3.6: Sub-partner Investment Adjustment (Private)
- Story 3.7: Edit an Investment Transaction (Audited)
- Story 3.8: Cancel/Reverse an Investment Transaction

## Requirements & Constraints

- A funding requirement needs only an amount and a date/cycle; ₹0 or negative is rejected with a clear validation message. Only Owner/Admin can create one; a non-Owner/Admin attempt (including direct API call) is a 403.
- Should Pay = Share % × requirement amount, computed per Partner and, one level down, per Sub-partner (their % of the *full* Project × requirement amount) — displayed with zero manual math required from the viewer, and accompanied by a worked-example hint at point of use (e.g. "Share 50% means if the project needs ₹10,00,000, your normal share is ₹5,00,000"), not a hover tooltip. When a split doesn't divide evenly, the remainder is allocated by the largest-remainder method and the sum of all Should Pay values equals the requirement amount exactly.
- Paid Now accepts any non-negative amount — 0, less than, equal to, or more than Should Pay — never blocked or auto-capped, and never alters Share %. Recorded fields: Project, Person, Amount, Date, Payment Mode (Cash, Cheque, NEFT, RTGS, IMPS, UPI, Bank Transfer, Other), Reference Number, Notes.
- Investment Adjustment per cycle: `New Adjustment = Recommended Amount − Actual Amount` — positive is Pending, negative is Extra Paid — stored per person, per Project, independent of Withdrawal Adjustment (never netted against it automatically; only an explicit, separately audited Owner/Admin action can offset the two).
- Next cycle's Recommended Amount = Base Amount (Share % × new requirement) + Previous Pending − Previous Extra Paid, shown alongside the plain Normal Share; remains freely editable by Owner/Admin when recording the actual payment. Adjustments are per-person, not pooled — one person's carry-forward never affects another's Should Pay. Any remaining gap keeps carrying forward round over round.
- The same Should Pay → Paid Now → Adjustment → Carry Forward logic applies privately within a Partner's own Sub-partner allocation — visible only to that Partner, their own Sub-partners, and Owner/Admin; a 403 for any other Partner (enforced by Epic 2's privacy gate, not a new mechanism).
- Editing a recorded transaction's amount or details preserves who changed it, when, and the old/new values in the audit trail, visible to Owner/Admin and to the transaction's own Partner/Sub-partner; changing the amount recomputes that transaction's Investment Adjustment.
- Cancelling/reversing a transaction never hard-deletes it: the original record is preserved with status "cancelled" plus a linked reversal record, and the cancelled amount stops counting toward Paid Now the next time the adjustment ledger is viewed. Only Owner/Admin can cancel/reverse; anyone else attempting it gets a 403.
- A double-submitted request (same idempotency key) reaching the server twice creates exactly one transaction record.
- Dashboards, Money History, and report views touching this epic's data must still return in under 2 seconds at expected data volume (no automated perf check exists yet — manual review criterion).

## Technical Decisions

- **AD-4 (new this epic) — separate, share-keyed ledgers:** `investment_adjustments` and (later, Epic 4) `withdrawal_adjustments` are two distinct tables, each keyed by `(shareId, projectId)` — `shareId` is `PARTNER_SHARE.id` or `SUBPARTNER_SHARE.id`, **never `USER.id`**. This lets a Sub-partner accrue adjustment history against their share record before any login exists for them; a login, when created later, links to the existing share rather than the ledger re-keying to it. No code path reads one ledger (Investment) to compute or silently offset the other (Withdrawal) — netting is its own explicit, audited transaction type, never a side effect of either cycle's calculation.
- **AD-5 (new this epic) — audited, transactional, idempotent financial writes:** every create/edit to a financial record (`investment_transactions`, and their `investment_adjustments` recomputation) runs inside one DB transaction that also writes an `audit_log` row (actor, timestamp, old value, new value, reason) in that same transaction. Every financial-write endpoint requires a client-generated idempotency key, stored with a unique constraint; a repeated request with the same key returns the original result rather than creating a second record. "Delete" is implemented only as `status: cancelled` plus a linked reversal record — no `DELETE` statement ever targets `investment_transactions` or `audit_log`. This pattern (tables + idempotency-key constraint + cancel/reverse convention), once built in Story 3.3/3.7/3.8, is reused unchanged by every later financial-write story in Epic 4 — not reinvented.
- Builds on Epic 2's proven foundations: `authorize()`/`authorizeScope()` (AD-1) gates every route in this epic exactly as it did Epic 2's — no second access-control mechanism; a denied request is 403 with no data body. AD-3's already-shipped, unconditional Share % versioning means every Should Pay calculation here reads the `sharePercent` effective at calculation time and **snapshots it onto the transaction row itself** — a transaction never recomputes its historical share from current `PARTNER_SHARE`/`SUBPARTNER_SHARE` state, so a later Share % edit can never silently rewrite a past round's Should Pay.
- **AD-2 governs all money/percent math in this epic**, reusing `packages/core/src/decimal-math.ts` (already shipped: `toPercent()`, `sumPercents()`) and extending it with the money-side equivalents this epic needs (largest-remainder split of an amount across people, Should Pay / Adjustment arithmetic) — no other file performs `+`/`-`/`*` on a monetary value directly, and no `Number()`/`parseFloat` touches a monetary or percentage value outside this module. Money is stored as Postgres `NUMERIC` and must cross every boundary (DB row, domain function, API response, UI prop) as a nominally-branded `Money` value type in `packages/types` — this type does not exist yet in the codebase (only `Percent` has shipped) and needs adding as part of this epic's first money-handling story.
- New tables this epic owns: `investment_requirements` (3.1), `investment_transactions` + `audit_log` + its idempotency-key unique constraint (3.3), `investment_adjustments` (3.4). All new tables follow the existing conventions: UUID v7 ids, `snake_case` columns, domain identifiers mirroring PRD Glossary terms verbatim (`shouldPay`, `extraPaid`, etc. in code).
- Dependency direction is unchanged and lint-enforced: this epic's calculation engine (Should Pay, Adjustment, carry-forward) belongs in `packages/core`; `packages/core` imports only `packages/types`, never `packages/db`; Route Handlers never call Drizzle directly for a write, only a `packages/core` service function wrapped in one DB transaction.

## UX & Interaction Patterns

- Add Money is a tabular, per-Project-scoped screen (same data-table-with-sub-rows pattern as Partner Shares: right-aligned numeric columns, Sub-partners one indent level under their Partner with a `↳` prefix, a table-foot privacy note) — reuses the existing `ShareRow`/`DistributedCheck` component pair and table pattern rather than a new one.
- Every Should Pay / Adjustment figure needs its worked-example hint visible at point of use, not a hover tooltip — same pattern already proven on Partner Shares' Share % field. A person's Add Money view shows "Normal Share: ₹X" and "After Previous Adjustment: ₹Y" side by side once a carry-forward exists.
- Recording a payment surfaces a status chip next to the person's row immediately (`success` for Extra Paid, `danger` for Pending) — paired with a label + amount, never a bare color dot — and a confirmation message that's explicit and plain-language (e.g. "₹2,00,000 added to Project A for Partner A"), never a generic "Success" toast.
- A Sub-partner's private Investment Adjustment renders only within their Partner's own scoped view (Partner detail / that Partner's own dashboard) — never surfaced to a co-Partner, identically to Epic 2's privacy boundary; a denied view is the plain "You don't have access to this" surface with no data hint.
- Money values render with the same tabular-numeral, Indian-digit-grouping formatting as Share %, and this epic's amounts are the first real consumer of the `Money`-typed `Amount` display treatment in `packages/ui`.

## Cross-Story Dependencies

- Within Epic 3, dependencies follow FR ordering: **3.1 (Requirement) → 3.2 (Should Pay)** — Should Pay has nothing to calculate against until a requirement exists. **3.2 → 3.3 (Paid Now)** — a Should Pay line is what Paid Now is recorded against. **3.3 → 3.4 (Adjustment)** — an adjustment needs an actual transaction to compare against Should Pay. **3.4 → 3.5 (Carry Forward)** — carry-forward reads the previous cycle's computed adjustment. **3.6 (Sub-partner)** depends on 3.2–3.5's logic existing at the Partner level first — it applies the identical calculation one level down, privately. **3.7 (Edit)** and **3.8 (Cancel/Reverse)** both depend on 3.3's transaction + audit_log + idempotency-key foundation existing first — they extend it (edit recomputes 3.4's adjustment; cancel un-counts a transaction from the ledger 3.4 built), not reinvent it.
- Epic 3 depends on the whole of Epic 2: Should Pay/Adjustment calculations require finalized, versioned Partner/Sub-partner Share % (Epic 2's `partner_shares`/`subpartner_shares`, AD-3), and this epic's requirement-creation flow assumes Partner Shares already exist on the Project. Story 3.6's privacy enforcement is Epic 2 Story 2.4's co-partner boundary applied to new data, not a new mechanism.
- Epic 4 (Withdraw Money) depends on this entire epic: it reuses AD-4's ledger-per-share pattern (adding `withdrawal_adjustments` alongside `investment_adjustments`) and AD-5's audit/idempotency/transaction/cancel-reverse pattern verbatim, established here in Stories 3.3, 3.7, 3.8.
