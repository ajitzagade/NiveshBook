## Intent

**Problem:** Can Take (Story 4.1) is a live calculation with nothing recorded against it — nobody can record an actual withdrawal ("Take Now"), and there's no audit trail or protection against a double-submitted form creating two transactions for one real withdrawal.

**Approach:** New `withdrawal_transactions` table (one row per recorded withdrawal, keyed by `(partyType, shareId)`, mirroring `investment_transactions`), written via one atomic DB transaction with its paired `audit_log` row (AD-5, table reused unchanged from Epic 3). `sharePercentSnapshot`/`canTakeSnapshot` are snapshotted at creation time by re-running Story 4.1's `computeCanTake` server-side (AD-3) — never trusting a client-submitted value, needed by Story 4.3's Withdrawal Adjustment. Project-scoped only (no requirement-equivalent entity, mirroring Story 4.1's URL shape): `POST /api/projects/[id]/withdrawal-transactions`. `withdrawal_transactions:create` opens self-access (a Partner/Sub-partner records their own withdrawal; Owner/Admin records anyone's), mirroring `investment_transactions:create`'s precedent exactly. The UI extends Story 4.1's existing Withdraw Money page with a "Record Withdrawal" dialog per row, mirroring Add Money's dialog.

**Decisions (resolved 2026-09-24):**
- **`canTakeSnapshot`/`sharePercentSnapshot` are captured, not dropped** — despite no requirement entity existing, AD-3 requires Can Take's effective share % and computed entitlement snapshotted onto the row, exactly mirroring `shouldPaySnapshot`'s role for Story 4.3's later Adjustment computation.
- **No cap against Can Take in this story.** Mirrors Story 3.3's identical precedent (Paid Now is never capped against Should Pay) — any amount, including one exceeding Can Take, is accepted and recorded as-is. Extra Withdrawal's explicit authorization gate is Story 4.5's job, not this one's.
- **No `status`/`reversalOfTransactionId` column yet.** Mirrors `investment_transactions`' original Story 3.3 shape before Story 3.8 added them — building them speculatively now, ahead of Story 4.11's real need, is exactly the ahead-of-a-consumer capability this codebase has consistently avoided. Story 4.11 adds them via its own migration.
- **Idempotency-key discipline, baked in from the start (lessons already paid for once in Story 3.3's own review, not to be re-discovered here):** (1) the client mints the idempotency key once per logical submission — on dialog open, not inside the fetch helper — and reuses it across a retry; (2) the port's replay lookup validates the found row's content (`projectId`/`partyType`/`shareId`/`amount` via a decimal-safe comparison) against the incoming request before treating it as a replay, throwing `IdempotencyKeyConflictError` (409) on a genuine mismatch rather than silently returning unrelated data; (3) that content comparison uses a `moneyEquals`-style decimal-safe check (reuse `packages/core/src/decimal-math.ts`'s existing `moneyEquals`), never raw string equality — Postgres's `numeric(14,2)` round-trips `"250000"` as `"250000.00"`, and a legitimate identical-content retry must succeed as a 200 replay, not 409.
- **`referenceNumber`/`notes` normalize an explicit empty string to `null` server-side**, not just client-trimmed (Story 3.3's patch-round fix, applied here from the start).
- **`PaymentMode` (`packages/types`) is reused unchanged** — already generic, not investment-specific.
- **The port's atomic-write + idempotency-race-recovery path gets a real live-Postgres integration test** (mirroring Story 4.1's `investment-transaction-port.test.ts` pattern, established during that story's own review as this codebase's now-standard way to cover a port's real SQL), not just a mocked-port route test.

## Boundaries & Constraints

**Always:** `POST /api/projects/[id]/withdrawal-transactions` requires a valid session (401). Resolves the target Partner/Sub-partner's current share (404 if `shareId`/`partyType` doesn't match any current share for this Project) before calling `authorize()` for `"withdrawal_transactions:create"` with `resourceRef.ownerId` set to that share's `userId` (self-access allowed; Owner/Admin always allowed; anyone else 403). Project existence is checked before any share/transaction read. `amount`/`transactionDate`/`paymentMode` are validated before any write; Can Take's own preconditions (Partner Shares total 100%, no Sub-partner over-allocation — reused from Story 4.1) are re-checked at write time and mapped to the same 409 codes. Every successful `POST` writes the transaction row and one `audit_log` row (`entityType: "withdrawal_transaction"`) in a single DB transaction; a repeated `POST` with the same `idempotencyKey` and matching content returns the original row (200, not 201).

**Never:** No edit/cancel endpoint (Story 4.11). No Withdrawal Adjustment computation (Story 4.3) — this story only records the raw transaction plus its Can Take snapshot. No change to a Partner/Sub-partner's `sharePercent`. No cap/rejection when `amount` exceeds `canTakeSnapshot` (see Decisions). No `DELETE` ever targets `withdrawal_transactions`.
