## Intent

**Problem:** FR-32 ("the read path for FR30's trail") asks for a way to jump between linked transactions from Money History. Story 4.10 already built the full data layer (`assembleMoneyTrail()`, `reconcileMoneyTrail()`, `GET /api/money-trail`) but deliberately shipped no UI, explicitly deferring the Trail/TraceBanner visual component to this story. Story 5.1 built the Money History list this story links from. `packages/ui`'s `Trail`/`TrailItem`/`TraceBanner` components already exist (built ahead during Story 4.10, unused since — confirmed via `packages/ui/src/components/trail.tsx`). What's missing: the trigger mechanism (EXPERIENCE.md flags this as an explicit, unresolved `[ASSUMPTION]`), the `MoneyHistoryEntryType → MoneyTrailNodeType` mapping (doesn't exist anywhere), and `money_trail:view`'s self-access (still Owner/Admin-only, deliberately deferred by Story 4.10 to "a later Epic 5 broadening").

**Approach:** Confirmed with the user 2026-09-25:
1. **In-place swap via query param**, not a dedicated route. Clicking a linked entry's row on `/money-history` adds `?traceType=X&traceId=Y`, swapping the page's content area from the flat list to `TraceBanner` + `Trail` (with a clear way back). Matches the mockup's own footnote ("jump into its money trail") and DESIGN.md's "one hero visualization per screen" rule; reuses this page's existing query-param-driven pattern from Story 5.1's filters — no new route.
2. **Trail Quick View (horizontal branching) is out of scope.** DESIGN.md/EXPERIENCE.md both frame it as an optional alternate rendering of identical data that *replaces* the vertical Trail when toggled, never a co-required second view — the vertical Trail alone satisfies "entire trail is reachable." It has zero existing implementation (unlike the vertical Trail); pulling it in would be a much larger, separately-scoped lift.
3. **`money_trail:view` gets real self-access, but scoped only at the starting point — not by redacting mid-tree nodes.** A Partner/Sub-partner can only *start* a trail from an entry that's genuinely their own (resolved via the same current-share lookup Story 5.1 built); once authorized, the assembled trail shows every connected node regardless of which other parties it involves — mirrors the established precedent that Add Money's "Moved from Project A" indicator is already shown transparently for movement bundles, and matches this story's own AC literally ("the entire trail... is reachable"). No redaction logic invented.
4. **Self-access uses `SCOPE_SELF_ACCESS_ACTIONS`** (not `SELF_ACCESS_ACTIONS`) — mirrors `partner_shares:list`'s exact precedent (`authorize.ts:339-357`): the route resolves the starting entity's owning `userId` via a narrow lookup *before* calling `authorizeScope()`, passing it as a single-element `scopeOwnerIds`. This narrow identity-resolution read (the same row `assembleMoneyTrail()` would fetch anyway as its root node) happening before authorization is the same accepted shape `partner_shares:list` already uses, not a new AD-1 violation — noted explicitly since a superficially similar case was flagged as a genuine violation elsewhere (an *unrelated* existence check, not an identity-resolution read the scope mechanism itself requires).

## Boundaries & Constraints

**Always:** The route resolves the starting entity's owning party (via `findById` + a current-share lookup) before calling `authorizeScope()` (AD-1's spirit — no data BEYOND the narrow identity-resolution read happens before authorization). `assembleMoneyTrail()`/`reconcileMoneyTrail()` (Story 4.10) are called exactly as they are today — no signature change. The `MoneyHistoryEntryType → MoneyTrailNodeType` mapping is exhaustive (every one of Story 5.1's 6 entry types maps to exactly one of the 4 startable `MoneyTrailNodeType`s, confirmed 1:1 during investigation).

**Never:** No change to `assembleMoneyTrail()`, `reconcileMoneyTrail()`, or the existing `GET /api/money-trail` route's core assembly/reconciliation logic — only its authorization gate changes. No Trail Quick View / horizontal branching UI (Decisions #2). No per-node redaction of other parties' details within an assembled trail (Decisions #3). No new dedicated route/page for the trail view (Decisions #1).

## Implementation Notes

**Route self-access resolution (`apps/web/app/api/money-trail/route.ts`):** `type`/`id` parsing was moved to run BEFORE authorization (previously it ran after) -- the self-access check itself needs `type`/`id` to resolve a `scopeOwnerIds` candidate, so this reordering is required, not incidental. The actor's role is read once via `userPort.findUserById()` purely to decide whether to skip the narrow identity-resolution read (`resolveTrailStartOwner()`) for `owner_admin` -- `authorizeScope()` re-reads the actor's role itself right after anyway (never cached, AD-1), so this is a harmless second read, mirroring `money-history/route.ts`'s own established double-fetch pattern. `resolveTrailStartOwner()` fetches only ONE of `listAllCurrentPartnerShares()`/`listAllCurrentSubPartnerShares()` (whichever the resolved `partyType` needs), not both -- narrower than `money-history/route.ts`'s own always-fetch-both approach, since here the `partyType` is already known from the entity lookup itself. For `withdrawal_destination_allocation`, if the leg exists but its parent withdrawal can't be found (a data-integrity edge case, not expected in practice), the route treats it as `{ found: true, ownerId: null }` rather than a 404 -- the leg itself does exist, so 404 would misrepresent that; self-access is simply not granted (falls through to the owner_admin-only role check) rather than fabricating either an authorization grant or a not-found error.

**Route test additions (`route.test.ts`):** the pre-existing "returns 403 for a non-Owner/Admin session, before any data read" test was rewritten -- under the old Owner/Admin-only gate, a Partner was rejected purely by role, before any read; under Story 5.2's self-access gate, a Partner IS resolved (the identity-resolution read now happens) and THEN rejected if the resolved owner doesn't match. The test now asserts `investmentTransactionFindById` was called (once) instead of asserting it wasn't.

**Tree-flattening approach (`apps/web/lib/money-trail-view.ts`'s `flattenTrail()`, extracted from `page.tsx` during review):** a plain "walk `root`'s own `upstream`/`downstream` recursively" DFS is NOT sufficient to reach every node in the tree. Reason: an intermediate ancestor's own `downstream` can re-expand sibling branches the starting node's own subtree never reaches -- concretely, starting from one `withdrawal_destination_allocation` leg, walking up reaches its parent `withdrawal_transaction`, whose `downstream` is EVERY leg of that withdrawal (via `listByWithdrawalTransactionId`), not just the leg you started from. This is exactly how the worked-example's "one withdrawal split into 3 legs" becomes fully reachable when starting from any single leg -- the acceptance criterion literally requires this.
**Correction (Review Triage Log row 1):** the first shipped version of this function visited `root`'s ancestors first and `root` itself last, on the theory that dedup made the ordering "free." That was wrong -- it caused a real, verified bug: `assembleMoneyTrail()`'s cycle-protection makes `root` reappear elsewhere in the SAME tree as a truncated stub (same key, `upstream: []`/`downstream: []`) whenever an ancestor's own `downstream` lists every child including the one the trail started from. Visiting ancestors first let that stub claim `root`'s dedup key before the real `root` object (with its real `upstream`/`downstream`) ever got a turn, permanently shadowing it -- silently dropping an entire reachable subtree (a leg's own downstream reinvestment chain) and mis-coloring a reinvestment `investment_transaction` traced directly as a true origin. The fix: call `visit(root)` FIRST, claiming its key with its real children immediately, so any later-encountered stub of the same node correctly no-ops instead of shadowing it. Once `visit(root)` runs first, it alone is sufficient -- it already recursively explores both `upstream` and `downstream` at every node it touches, reaching everything in the same connected component (including every ancestor and everything reachable from each ancestor's own downstream); the separate "walk to the true origin, then visit ancestors, then root" staging was removed as dead code once traced through (it never actually contributed anything `visit(root)` alone didn't already cover). This does mean the flattened order is no longer strictly "true origin first, chronological" -- it's `root` first, then a DFS outward in both directions -- which is an accepted tradeoff of correctness over that particular cosmetic ordering nicety (never a graded requirement; only "every node exactly once, no infinite loop" was). Regression tests live in `apps/web/lib/money-trail-view.test.ts`, verified to actually fail against the old ancestors-first ordering before being confirmed against the fix.

**Dot-color-per-node-type choices (`describeTrailNode()`):** sourced directly from `DESIGN.md`'s own "Colors" section, which ties each of the 5 semantic colors to a transaction *meaning*, not a fixed per-component color -- applied literally, not invented: `success` (green) for `investment_transaction` at a true origin ("money added"); `amber` for an `investment_transaction` reached as a reinvestment (`node.upstream.length > 0`, i.e. auto-created via a `money_movement`) -- this is a deliberate, non-obvious split of the SAME node type by structural position in the tree, directly justified by DESIGN.md's own literal phrase "amber: a later/secondary reinvestment step in a money trail"; `danger` (red) for `withdrawal_transaction` ("a withdrawal event", a neutral fact in this context, not "owed money" -- no ambiguity since danger is never used for an adjustment here); `info` (teal) for a `"project"`-destination `withdrawal_destination_allocation` leg AND for `money_movement` nodes ("money movement between projects" -- DESIGN.md's exact phrase for both); `violet` for a `"person"`/`"other"`/`"available_balance"`-destination leg, `available_balance_spend`, and `available_balance_pool` (DESIGN.md ties violet to both "Available Balance" and "a transfer to a person"); `ink-faint` (neutral) for `project_investment_pool` -- the one node type with no real DESIGN.md mapping, since it's a derived aggregate reference rather than a real transaction event, so a neutral/muted treatment was chosen deliberately rather than reusing one of the 5 meaningful colors out of context. All values are passed as CSS custom-property references (e.g. `"var(--color-amber)"`) into `TrailItem`'s existing `dotColor` prop, never a new hardcoded hex value.

**Filter-preservation approach:** the Code Map's "mirrors this page's existing query-param-driven filter pattern" turned out not to literally apply -- Story 5.1's flat-list filters (date/project/person) are local React component state, not URL query params (confirmed by reading the actual shipped page, not just the spec's paraphrase). Rather than migrating those filters to the URL (out of scope, not requested), only the new `traceType`/`traceId` params are URL-driven. Since entering/leaving trace mode is a same-route client-side `router.push()` (not a full navigation), the page component instance is never unmounted, so the existing filter state simply survives the round trip with no extra plumbing -- "Back to list preserves existing filters" holds trivially as a side effect of this, not because filters are also URL-encoded.
**Correction (Review Triage Log row 3):** the original test claiming to verify this pushed a synthetic `projectId` URL param through the mocked `searchParams` and asserted the URL string `handleBackToList()` built -- it never actually exercised the claimed mechanism, since the page never reads `searchParams.get("projectId")` anywhere. Replaced with a test that applies a REAL filter through the filter form (setting actual `formFilters`/`appliedFilters` state), uses React Testing Library's `rerender()` on the SAME component instance to simulate the URL changing into and back out of trace mode (mirroring how Next.js re-renders the same page component in place on a client-side `router.push()`, without unmounting it), and asserts the Project `<select>` still shows the earlier selection afterward -- proving component state genuinely survives the round trip, not just that `handleBackToList()`'s own string-building is correct.
